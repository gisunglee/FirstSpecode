# UW-00036 구현 변경 스펙 정합성 관리

> 요구사항: RQ-00070  
> 프로세스: PID-00063 스펙 동기화, PID-00064 동기화 검토  
> 상태: V2 구현 완료 · 운영 재검증 전

## 1. 목적

SPECODE 밖에서 수정한 현재 소스를 현재 UW 설계와 비교한다. 모든 설계 대상을 점검하되 정상은
수치로만 남기고, 사람이 판단할 문제와 설계 수정 후보만 저장·검토·반영한다.

Git commit, Diff, provider, source baseline은 필수가 아니다.

## 2. 실행 방식

```text
/sync-specode UW-XXXXX          기본 점검(CHECK)
/sync-specode UW-XXXXX --deep   정밀 동기화(DEEP_SYNC)
```

1. Worker key가 가리키는 프로젝트명·ID, UW, 모드를 사용자에게 확인받는다.
2. 현재 UW 설계 snapshot을 한 번 받아 작은 target 묶음으로 나눠 읽는다.
3. 관련 소스를 찾고 불확실한 범위만 사용자에게 확인받는다.
4. 관련 파일의 SHA-256을 고정하고 모든 설계 target을 점검한다.
5. 정상은 `evaluatedTargets`로만 증명하고 문제만 상세 결과로 만든다.
6. 제출 직전 파일 hash를 다시 확인하고 helper가 근거 snippet을 만들어 직접 제출한다.
7. 권한 있는 사용자가 웹에서 문제를 적용·거부·보류한다.

## 3. 판정

### 구현 정합성

- 정상은 상세 item을 만들지 않는다.
- `MISMATCH`: 동일 동작의 설계와 구현이 다름
- `NOT_IMPLEMENTED`: 설계에 있으나 구현 근거가 없음
- `UNKNOWN`: 근거 또는 범위를 확정할 수 없음

### 설계 커버리지

- `IMPORTANT_GAP_CANDIDATE`: CHECK에서 찾은 중요한 설계 누락 후보
- `GAP_CANDIDATE`: DEEP_SYNC에서 찾은 일반 누락 후보
- `STRUCTURE_GAP`: 신규 화면·영역·기능 등 구조 설계 필요
- `UNKNOWN`: UW 의도나 범위를 확인해야 함

소스에 기능이 더 많다는 이유만으로 구현 불일치로 판정하지 않는다.
불일치가 명확한지와 안전한 설계 수정안을 만들 수 있는지는 별개다. 수정안을 확정할 수 없어도
판정은 유지하며, 이 경우 적용 버튼 없이 거부·보류만 제공한다.

## 4. 화면

### 목록 `/projects/{projectId}/spec-reconciliations`

- UW, 모드, 구현 정합성, 설계 커버리지, 상태, 요청자, 요청일
- 점검 대상 수, 구현 정상 수, 문제 수, 결정 대기 수
- 정상 상세 카드는 표시하지 않는다.

### 상세 `/projects/{projectId}/spec-reconciliations/{runId}`

- 상단에 `점검 대상 / 구현 정상 / 문제` 요약
- AI의 긴 실행 요약 원문은 상단에 반복 표시하지 않는다.
- 불일치·미구현·판단 불가·설계 누락 후보만 표시
- 문제별 설계 내용, 소스 사실, 판정 이유, redacted 코드 근거
- 수정 가능한 항목은 분석 당시 값(AS-IS), 현재 값, 제안 값(TO-BE)과 적용 버튼
- 수정안이 없는 항목은 거부·보류만 제공

## 5. 적용 규칙

- `APPLY | REJECT | DEFER`는 `PENDING` 문제에만 허용한다.
- `APPLY`는 수정안이 있어야 하며 PM·PL·OWNER·ADMIN만 실행한다.
- 제안 대상 설명 필드의 현재 exact hash가 분석 당시 `before_hash`와 같을 때만 반영한다.
- hash가 다르면 `DESIGN_CHANGED`로 바꾸고 분석 당시 값·현재 값·제안 값을 보여준다.
- 자동 병합이나 덮어쓰기는 하지 않는다.

## 7. 저장 테이블

- `tb_sp_sync_run`: 실행 대상, 모드, 설계 snapshot, 소스 범위, 판정 및 건수 요약
- `tb_sp_sync_item`: 문제 상세, 근거, 수정안, 사람의 결정 및 적용 이력
- `tb_ds_design_change`: 승인된 설계 변경 이력

정상 항목은 `tb_sp_sync_item`에 저장하지 않는다. 소스 원문·전체 Diff도 저장하지 않는다.

## 8. 완료 조건

- 모든 snapshot target이 정확히 한 번 점검된다.
- 정상 상세 제출·DB item·화면 카드가 0건이다.
- 문제에는 검증 가능한 path·line·snippet·hash가 있다.
- 분석 중 소스가 바뀌면 제출이 차단된다.
- 프로젝트·UW가 사용자 확인 없이 잘못 선택되지 않는다.
- 승인되지 않은 제안 또는 변경된 설계를 자동 반영하지 않는다.
- CHECK와 DEEP_SYNC는 각각 운영 검증을 통과한 범위부터 배포한다.
