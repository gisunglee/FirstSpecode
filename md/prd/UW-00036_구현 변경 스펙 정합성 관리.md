## 2. 변경 유형

### 유형 A — 구현요청 결과가 요청 당시 스펙과 다름

```text
구현요청 스펙 snapshot
  → /run-ai-tasks IMP
  → 구현 전/후 source snapshot과 Diff
  → 요청 당시 스펙 대비 편차 후보
  → 스펙 반영함
```

제안의 `beforeValue/beforeHash`는 현재 스펙을 추측하지 않고 해당 구현요청의
`tb_sp_impl_snapshot` 원문과 hash를 사용한다.

### 유형 B — 개발 완료 후 소스를 직접 수정함

```text
마지막 source baseline C4
  → /sync-specode [UW-XXXXX]
  → 현재 source C5와 C4..C5 비교
  → 관련 설계 컨텍스트 조회
  → 편차 후보
  → 스펙 반영함
```

미커밋 변경도 `DRAFT`로 분석할 수 있지만 source baseline은 전진하지 않는다.
Git이 없으면 content-addressed `SOURCE_MANIFEST` snapshot으로 같은 흐름을 수행한다.

### 유형 C — Git provider PR/MR

```text
서명된 GitHub PR 또는 GitLab MR webhook
  → 서버가 provider API에서 commit·ancestry·Diff 재조회
  → PROVIDER_VERIFIED receipt
  → SPEC_RECONCILIATION AI 태스크
  → 스펙 반영함
```

## 5. 상태

### Receipt

| 코드 | 의미 |
|:-----|:-----|
| `DRAFT` | 미커밋 Git working tree 분석. 검토용이며 baseline 전진 금지 |
| `NEEDS_REVIEW` | 사람의 결정 또는 증거 확인 필요 |
| `CLOSED` | 모든 항목 해결·증거 확인·baseline 전진 완료 |
| `STALE_BASELINE` | 다른 receipt가 같은 baseline을 먼저 전진시킴 |

`review_sttus_code`는 `ANALYZING`, `ANALYSIS_FAILED`, `NEEDS_REVIEW`, `CLOSED`
등 AI 분석과 검토 상태를 별도로 표시한다.

### Item

| 코드 | 의미 |
|:-----|:-----|
| `PENDING` | 결정 대기 |
| `APPLIED` | 스펙 적용 완료 |
| `NO_SPEC_CHANGE` | 스펙 영향 없음 확정 |
| `AWAITING_SOURCE_FIX` | 보완 source checkpoint 대기 |
| `STALE_SPEC` | 후보 생성 후 스펙 변경. 3-way 병합 또는 재분석 필요 |
| `RESOLVED` | 예외·모델 보완·소스 보완 후속 처리 연결 |
| `ROLLED_BACK` | 과거 적용 취소. 자식 receipt로 재검토 생성 |

## 6. 증거 신뢰등급

| 등급 | 규칙 |
|:-----|:-----|
| `PROVIDER_VERIFIED` | SPECODE 서버가 연결된 GitHub/GitLab에서 base/head 존재, merge-base, 전체 Diff를 직접 검증 |
| `LOCAL_AGENT_ATTESTED` | 로컬 명령이 repo fingerprint, commit/manifest, ancestry, Diff hash를 수집 |
| `USER_UPLOADED` | 사람의 수동 입력. 단독 확정 금지, OWNER/ADMIN override 필요 |

보안 규칙:

- `.env`, 토큰, 인증서, private key, vendor/build 산출물을 snapshot에서 제외한다.
- provider token과 webhook secret은 AI provider key와 별도 테이블에 암호화 저장한다.
- 미커밋 Git head는 `WORKTREE:{manifestHash}`로 표시하고 `DRAFT`만 허용한다.
- provider compare가 잘리거나 timeout이면 `PROVIDER_VERIFIED`로 저장하지 않는다.
- 프로젝트 설정으로 CI gate를 `WARN`/`BLOCK`, 차단 위험도, source Diff 보관기간을
  관리한다. 기본값은 `WARN`, `HIGH,CRITICAL`, 90일이다.
- 보관기간이 지난 CLOSED receipt는 OWNER/ADMIN이 대상을 미리보고 `ConfirmDialog`에서
  영구 삭제를 다시 승인한 후 receipt·item·batch JSON의 patch/content만 정리한다. 경로·hash·checkpoint·결정
  이력은 유지한다.
- 미리보기 결과에는 대상 상태로 만든 token을 포함한다. 확인 전에 대상이나 보관 정책이
  달라지면 실제 정리를 거부하고 최신 미리보기를 다시 요구한다.

## 7. 스펙 후보

허용 필드:

```text
UNIT_WORK.unit_work_dc
SCREEN.scrn_dc
AREA.area_dc
FUNCTION.func_dc
```

한 후보는 다음을 분리해 저장한다.

```text
sourceFact       Diff로 확인된 사실
inferredImpact   AI가 해석한 영향
proposedValue    변경 후 설명 전체 값
beforeValue      분석 당시 설명 전체 값
beforeHash       beforeValue SHA-256
sourceEvidence   파일·심볼·patch 근거
risk/confidence  위험도·확신도
```

클릭 시 AI를 다시 호출하지 않는다. 적용 시 대상 PK·허용 필드·`beforeHash`를 검증하는
결정적 트랜잭션을 실행한다.

## 8. 사람의 결정

| 액션 | 실행 |
|:-----|:-----|
| `APPLY_SPEC` | 설명 필드와 `tb_ds_design_change`를 같은 트랜잭션으로 저장 |
| `FIX_SOURCE` | 보완 AI 태스크를 만들고 최종 commit/manifest 제출까지 대기 |
| `NO_SPEC_CHANGE` | 판단 근거를 저장하고 항목 종료 |
| `ACCEPT_EXCEPTION` | 담당자·만료일·후속 태스크를 저장 |
| `MODEL_GAP` | 설계 모델 보완 리뷰 요청 생성 |
| `DEFERRED` | 사유를 기록하되 미해결 상태 유지 |

낮은 위험도의 `IMPLEMENTATION_DETAIL`, `SPEC_CLARIFICATION`만 선택 일괄 적용한다.
하나라도 충돌하면 전체 트랜잭션을 rollback한다.

## 9. 충돌·rollback

```text
현재 hash == beforeHash
  → proposedValue 적용

현재 hash != beforeHash
  → base/current/proposal의 변경 줄이 겹치지 않음
      → 3-way merge preview를 사람이 확인 후 적용
  → 같은 구간 변경
      → STALE_SPEC, 최신 스펙 기준 재분석
```

확정 후 적용 취소는 현재 값이 당시 적용 값과 같을 때만 허용한다. 과거 receipt와 변경
이력은 보존하고, 현재 source baseline 기준의 자식 receipt를 만들어 다시 미해결 상태로
노출한다.

## 10. Source baseline

```text
(project, repoKey, branch)
  → commit SHA 또는 manifest hash
  → checkpointVersion
```

Receipt 종료 조건:

1. 모든 항목이 `APPLIED`, `NO_SPEC_CHANGE`, `RESOLVED` 중 하나다.
2. head가 확정 checkpoint다.
3. 증거가 확인됐다.
4. `USER_UPLOADED`이면 관리자 override와 사유가 있다.
5. 제출 당시 `baselineVersion`과 현재 version이 같다.

조건을 만족하면 receipt `CLOSED`와 baseline checkpoint/version 전진을 같은 트랜잭션에서
처리한다. 낙관적 update가 0건이면 스펙 변경까지 rollback하고 receipt를
`STALE_BASELINE`으로 표시한다.

제안이 0건이어도 자동 종료하지 않는다. 사람이 증거를 확인해야 baseline이 전진한다.
`PRE_IMPL`은 구현요청 스냅샷만 갱신하며 receipt 종료나 baseline 전진에 사용하지 않는다.

## 13. 완료 기준

- 유형 A와 B가 서로 다른 기준값으로 제출된다.
- 커밋하지 않은 변경과 비-Git 프로젝트도 Diff를 만들 수 있다.
- 단위업무·화면·영역·기능 설명 후보를 안전하게 적용한다.
- 3-way merge, 일괄 적용, rollback, 여섯 가지 결정이 동작한다.
- 증거 확인과 baseline 전진이 원자적이며 stale version을 차단한다.
- GitHub/GitLab provider 검증, 서명 webhook, CI 경고 gate가 동작한다.
- 설계 상세에서 미반영 변경 배지를 확인할 수 있다.
- Prisma migration, 타입 검사, 프로덕션 빌드, 병합/snapshot/DB 트랜잭션 테스트가 통과한다.

## 14. 대형 단위업무 자동 비교 배치

### 기능 요구사항

1. 사용자는 전체 변경 또는 UW ID만 제출한다.
2. 서버는 receipt 하나 안에서 source link와 설계 계층을 이용해 비교 배치를 자동 생성한다.
3. 분류가 필요한 파일은 router AI가 scope만 고른다.
4. Worker는 router가 만든 후속 batch task까지 재조회한다.
5. 배치별 결과는 대상·필드·before 원문/hash 검증을 통과해야 저장된다.
6. 모든 배치가 완료돼야 receipt item으로 병합된다.
7. 같은 대상의 다른 제안은 자동 선택하지 않고 사람이 하나를 고른다.
8. 한 배치 실패 시 완료 배치를 유지하고 실패 배치만 재시도한다.
9. 분석 중·부분 실패·충돌 상태에서는 receipt 확정과 일반 item 결정을 차단한다.
10. 파일과 Diff를 상한에서 조용히 버리지 않는다.
