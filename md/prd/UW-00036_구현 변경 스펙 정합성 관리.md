## 3. 동기화 모드

| 모드 | 목적 | 결과 범위 |
|:---|:---|:---|
| `CHECK` | 설계대로 구현됐는지 확인 | 설계 항목별 정합성 + 중요한 설계 누락 후보 |
| `DEEP_SYNC` | 현재 프로그램을 더 깊게 설계화 | 관련 소스의 업무 동작 목록 + 일반 누락까지 포함한 동기화 후보 |

기본값은 `CHECK`다. 추가 구현은 구현 정합성 실패로 합치지 않고 설계 누락 후보로 분리한다.

## 7. 적용 규칙

자동 적용 대상은 기존 단위업무·화면·영역·기능의 설명 필드다.

```text
UNIT_WORK.unit_work_dc
SCREEN.scrn_dc
AREA.area_dc
FUNCTION.func_dc
```

AI는 제안 값만 만든다. 서버가 실행 snapshot에서 정확한 `before_value`와 raw UTF-8
`before_hash`를 만든다.

UW 전체 snapshot hash는 비교에 사용한 의미 데이터만 canonical JSON으로 계산하며 수정일·수정자
등 운영 메타데이터는 제외한다. 전체 hash 변화는 안내용이고, 실제 적용 차단은 대상 필드의
`before_hash`로만 결정한다.

```text
현재 대상 hash == before_hash
  → 제안 적용 + tb_ds_design_change 기록

현재 대상 hash != before_hash
  → 자동 적용 중단
  → 분석 당시 / 현재 / 제안 값 표시
  → 최신 설계 기준으로 제안 재작성 또는 재실행
```

신규 화면·영역·기능 생성이 필요한 `STRUCTURE_GAP`은 V2에서 자동 적용하지 않는다.

## 8. 상태와 저장

### Run

`RUNNING`, `NEEDS_INPUT`, `NEEDS_REVIEW`, `COMPLETED`, `FAILED`, `CANCELLED`

### Item

`INFORMATIONAL`, `PENDING`, `APPLIED`, `REJECTED`, `DEFERRED`, `DESIGN_CHANGED`

| 테이블 | 역할 |
|:---|:---|
| `tb_sp_sync_run` | UW·모드·설계 snapshot·소스 범위·실행 요약 |
| `tb_sp_sync_item` | 결과·근거·AS-IS/TO-BE·사람 결정·적용 이력 |
| `tb_ds_design_change` | 승인된 실제 설계 변경 이력 |

source baseline, fingerprint, Diff, source link와 과거 결정 자동 재사용은 저장하지 않는다.

## 10. API·MCP

### Worker API

```text
POST /api/worker/spec-syncs
POST /api/worker/spec-syncs/{runId}/result
POST /api/worker/spec-syncs/{runId}/cancel
```

### Web API

```text
GET  /api/projects/{id}/spec-syncs
GET  /api/projects/{id}/spec-syncs/{runId}
POST /api/projects/{id}/spec-syncs/{runId}/result
POST /api/projects/{id}/spec-syncs/{runId}/items/{itemId}/decision
```

### MCP

```text
start_spec_sync
submit_spec_sync_result
list_spec_syncs
get_spec_sync
```

MCP로 설계를 적용하지 않는다.

결정 API는 `PENDING` 항목만 허용한다. `APPLY`에는 수정안이 필수지만, `STRUCTURE_GAP`처럼
자동 적용할 수 없는 항목은 수정안 없이도 `REJECT/DEFER`할 수 있다. `INFORMATIONAL`, 이미
결정된 항목, 수정안 없는 항목의 `APPLY`는 `409 INVALID_ITEM_STATE`로 거부한다.
자동 적용안은 구현 `MISMATCH`와 기존 설명에 대응되는 설계 누락 후보에만 허용한다.
`NOT_IMPLEMENTED`, `UNKNOWN`, 구조 누락과 정보성 판정에는 만들지 않는다.

## 11. 보안

- secret, 인증서, private key, vendor, build, generated 경로를 분석·전송에서 제외한다.
- 로컬 helper가 저장소 밖 경로와 evidence snippet의 실제 일치 여부를 검증한다.
- 테스트 코드는 보조 근거로만 사용하며 현재 구현을 확정하는 유일한 근거로 허용하지 않는다.
- 서버에는 전체 소스 대신 검토에 필요한 최소 redacted snippet만 저장한다.
- AI 결과의 대상 ID가 실행 UW 계층에 속하는지 서버가 검증한다.

## 12. 인수 기준

1. 기본 점검이 설계 구현 여부와 중요한 누락 후보를 분리한다.
2. 정밀 동기화가 일반 설계 누락까지 더 넓게 찾는다.
3. 관련 소스가 불확실하면 사용자 확인 또는 `UNKNOWN`으로 남긴다.
4. Git 없이 동작한다.
5. 승인되지 않은 제안은 설계를 변경하지 않는다.
6. 제안 대상 설계가 바뀌면 자동 덮어쓰지 않는다.
7. 실제 파일과 일치하지 않는 코드 근거를 저장하지 않는다.
8. 같은 설계 필드의 동시 승인은 행 잠금과 exact hash로 하나만 성공한다.
9. `CHECK`는 실제 Shadow 검증 승인 전 `SPEC_SYNC_ENABLED=false`로 접수를 차단한다.
10. `DEEP_SYNC`는 별도 Shadow 검증 승인 전 `SPEC_SYNC_DEEP_ENABLED=false`로 차단한다.
11. V1 provider·baseline·Diff·receipt·batch 경로가 전환 후 남지 않는다.
