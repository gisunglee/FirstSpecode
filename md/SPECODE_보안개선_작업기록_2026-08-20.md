# SPECODE 보안 개선 작업 기록 (2026-08-20)

## 목적

- 기준 감사 문서 `SPECODE_전체_보안감사_2026-08-20.md`는 수정하지 않는다.
- 회귀 위험을 충분히 분석하고 자동 검증할 수 있는 보안 개선만 반영한다.
- 운영 방식 변경, 동시성 문제, 광범위한 성능 저하 가능성이 있는 항목은 보류 사유와 후속 검증 조건을 남긴다.

## 작업 원칙

1. 변경 전 타입 검사, 기존 핵심 테스트, 프로덕션 빌드의 통과 상태를 기준선으로 삼는다.
2. 인증 인터페이스(URL, 요청 파라미터, 응답 계약)는 변경하지 않는다.
3. 기존 정상 사용자와 현재 MCP 도구가 사용하는 경로를 먼저 조사한 뒤 허용 범위를 좁힌다.
4. 보안 경계의 핵심 판단은 순수 함수로 분리해 회귀 테스트를 추가한다.
5. 매 요청마다 새로운 DB 조회를 추가하는 변경은 실제 조회 지연을 고려해 적용하지 않는다.

## 이번 안전 적용 범위

- MCP CLIENT 키가 호출할 수 있는 HTTP 경로와 메서드를 명시적으로 제한한다.
- MCP 키 소유 회원이 ACTIVE인지 기존 키 조회 안에서 함께 검증한다.
- Access Token의 알고리즘과 필수 클레임을 런타임에서 검증하고 토큰 종류 혼동을 차단한다.
- 기존 30분 Access Token의 자연스러운 전환을 위해, 필수 클레임이 모두 있는 무표식 기존 토큰은 한시적으로 허용한다.
- 기존 DB 조회에 상태 필드를 추가하거나 기존 조회를 교체할 수 있는 경계에서 회원/세션 상태 검증을 강화한다.
- 이메일 회원가입 인증 토큰이 REGISTER 용도인지 확인한다.

## 명시적 보류 범위

- Refresh Token의 HttpOnly 쿠키 이전: PRD 간 저장 방식이 충돌하고 CSRF 방어·다중 탭 동기화·로그아웃 계약을 함께 설계해야 한다.
- 모든 JWT 요청의 세션 DB 실시간 검증: 측정된 DB 지연 때문에 요청당 추가 조회는 성능 회귀 위험이 높다.
- JWT issuer/audience 즉시 강제: 현재 발급 토큰 전체를 한 번에 무효화할 수 있어 단계적 전환 설계 없이 적용하지 않는다.

### 2026-08-20 — SEC-017 Refresh Token 원자적 회전·다중 탭 조정

- 서버는 `revoked_dt IS NULL`과 만료 시각을 조건으로 기존 RT를 1건만 소비하도록 변경했다.
- 기존 RT 소비, 연결 세션 유효성 재확인·접속 시각 갱신, 새 RT 생성을 하나의 DB 트랜잭션으로 묶었다.
- 두 요청이 같은 활성 RT를 동시에 읽어도 조건부 소비에 성공한 한 요청만 새 RT를 생성하며, 패배 요청은 `409 REFRESH_CONFLICT`를 반환한다.
- 방금 회전된 RT의 짧은 중복 요청은 정상 경쟁으로 분류해 세션을 종료하지 않는다. 유예 구간 이후 폐기 RT 재사용은 기존처럼 해당 세션의 활성 RT를 모두 폐기하고 세션을 무효화한다.
- 브라우저는 같은 출처 Web Locks로 탭 간 갱신을 직렬화하고, BroadcastChannel과 일시적인 storage event로 승자 결과를 대기 탭에 전달한다.
- 로그인 유지 RT는 localStorage가 탭끼리 자동 공유하므로 방송하지 않고, Access Token만 각 탭의 sessionStorage에 반영한다.
- 탭 전용 sessionStorage RT는 복제 탭을 지원하기 위해 회전 시에만 같은 출처 탭에 새 RT를 전달하며 영구 공용 저장소에는 쓰지 않는다.
- 로그인·회원가입 완료·소셜 로그인·소셜 연동의 토큰 저장을 공통 모듈로 통합해 local/session RT가 동시에 남지 않게 했다.
- 비밀번호 변경은 로그인 유지 여부와 관계없이 현재 RT를 정확히 전달해 현재 세션을 보존하고, 로그아웃·회원 탈퇴는 같은 출처의 다른 탭에도 즉시 전파해 남은 AT를 정리한다.
- 요청 본문과 성공 응답 계약, DB 스키마는 유지했다. MCP에 등록된 인증 갱신 도구가 없어 `register-tools.ts` 변경은 필요하지 않았다.

### 2026-08-20 — SEC-017 잔여 위험 재분석

- 로컬 실행 환경에는 Chrome 151과 Edge 151이 설치되어 있지만 Playwright·Puppeteer·Selenium 및 전용 드라이버는 설치되어 있지 않다.
- 실제 두 탭 E2E는 임시 PostgreSQL 스키마, 테스트 회원, 테스트 전용 Next.js 서버, 두 브라우저 탭을 함께 구동하는 별도 테스트 인프라로 구성해야 운영 데이터와 분리할 수 있다.
- 읽기 전용 운영 현황 확인 결과 활성·미만료 RT는 21개이며 `auto_login_yn='Y'`는 0개다. 활성 RT가 연결된 세션은 모두 생성 후 10일 이내다. 따라서 향후 RT 절대 수명을 도입해도 현재 활성 RT를 즉시 끊는 대상은 없다.
- 활성 세션 자체는 228개이고 90일 초과 세션이 126개지만, 이 중 활성·미만료 RT가 연결된 세션은 없다. 세션 정리 정책과 RT 절대 수명 정책은 별도 항목으로 다뤄야 한다.
- HttpOnly 쿠키 이전 영향 범위는 로그인, 가입 완료, 기존/신규 소셜 로그인, 소셜 연동의 RT 발급 5곳과 refresh, logout, 비밀번호 변경이다.
- 현재 일반 인증 경계에는 OAuth state 이외의 공통 Origin/CSRF 검증이 없다. 쿠키 이전 전 refresh/logout에 대한 동일 출처 검증을 먼저 추가해야 한다.
- 안전한 쿠키 이전 순서는 `Origin 방어 → 서버 dual-read/dual-issue → 브라우저 쿠키 사용 전환 → 안정화 확인 → 응답 body와 Web Storage RT 제거`의 단계 배포가 적합하다. 한 번에 전환하지 않는다.

## 남은 위험 항목

### 즉시 운영 조치가 필요한 항목

- SEC-001 원문 MCP 키: 사용자가 추후 직접 폐기하기로 결정해 이번 작업에서는 키·추적 파일·Git 이력을 변경하지 않았다.

### 설계 또는 동시성 검증이 먼저 필요한 항목

- HttpOnly Refresh Token 쿠키 이전: CSRF, Origin, 다중 탭, 로그인 유지, 로그아웃 계약과 충돌 PRD를 먼저 확정해야 한다.
- Refresh Token 절대 수명: 현재 자동 로그인은 회전할 때마다 만료를 10일 연장한다. 최초 발급 기준 최대 수명을 별도로 둘지는 제품 정책과 기존 장기 로그인 기대를 확정한 뒤 변경해야 한다.
- 모든 JWT 요청의 세션 실시간 조회: 현재 측정 지연(p95 약 984ms) 때문에 전역 적용하지 않았다. 고위험 API 선별 또는 캐시/토큰 버전 설계가 필요하다.
- SEC-003/007/013/015: 프로젝트 소유권·탈퇴·초대·일회용 토큰의 트랜잭션/불변식 변경은 운영 데이터 형태와 경쟁 요청 통합 테스트가 필요하다.
- SEC-005/006/009/010/011/016/018~022: HTML 정화, 테넌트 경계, 저장소, AI 실행, entitlement, 이메일 정규화, 운영 통제는 여러 화면/API/데이터 계약에 걸쳐 있어 항목별 PRD 대조와 전용 회귀 테스트 후 분리 적용해야 한다.
