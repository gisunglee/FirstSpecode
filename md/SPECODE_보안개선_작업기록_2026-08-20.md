## 목적

- 기준 감사 문서 `SPECODE_전체_보안감사_2026-08-20.md`는 수정하지 않는다.

## 작업 원칙

1. 변경 전 타입 검사, 기존 핵심 테스트, 프로덕션 빌드의 통과 상태를 기준선으로 삼는다.

3. 기존 정상 사용자와 현재 MCP 도구가 사용하는 경로를 먼저 조사한 뒤 허용 범위를 좁힌다.
4. 보안 경계의 핵심 판단은 순수 함수로 분리해 회귀 테스트를 추가한다.
5. 매 요청마다 새로운 DB 조회를 추가하는 변경은 실제 조회 지연을 고려해 적용하지 않는다.

- MCP 키 소유 회원이 ACTIVE인지 기존 키 조회 안에서 함께 검증한다.
- Access Token의 알고리즘과 필수 클레임을 런타임에서 검증하고 토큰 종류 혼동을 차단한다.

### 2026-08-20 — SEC-017 Refresh Token 원자적 회전·다중 탭 조정

> 이 절은 HttpOnly 전환 전 1차 구현 기록이다. 아래 `Refresh Token HttpOnly 쿠키 전환` 절이 현재 최종 브라우저 저장·공유 방식이다.

- 서버는 `revoked_dt IS NULL`과 만료 시각을 조건으로 기존 RT를 1건만 소비하도록 변경했다.
- 기존 RT 소비, 연결 세션 유효성 재확인·접속 시각 갱신, 새 RT 생성을 하나의 DB 트랜잭션으로 묶었다.
- 두 요청이 같은 활성 RT를 동시에 읽어도 조건부 소비에 성공한 한 요청만 새 RT를 생성하며, 패배 요청은 `409 REFRESH_CONFLICT`를 반환한다.
- 방금 회전된 RT의 짧은 중복 요청은 정상 경쟁으로 분류해 세션을 종료하지 않는다. 유예 구간 이후 폐기 RT 재사용은 기존처럼 해당 세션의 활성 RT를 모두 폐기하고 세션을 무효화한다.
- 브라우저는 같은 출처 Web Locks로 탭 간 갱신을 직렬화하고, BroadcastChannel과 일시적인 storage event로 승자 결과를 대기 탭에 전달한다.
- 로그인 유지 RT는 localStorage가 탭끼리 자동 공유하므로 방송하지 않고, Access Token만 각 탭의 sessionStorage에 반영한다.
- 탭 전용 sessionStorage RT는 복제 탭을 지원하기 위해 회전 시에만 같은 출처 탭에 새 RT를 전달하며 영구 공용 저장소에는 쓰지 않는다.
- 로그인·회원가입 완료·소셜 로그인·소셜 연동의 토큰 저장을 공통 모듈로 통합해 local/session RT가 동시에 남지 않게 했다.
- 비밀번호 변경은 로그인 유지 여부와 관계없이 현재 RT를 정확히 전달해 현재 세션을 보존하고, 로그아웃·회원 탈퇴는 같은 출처의 다른 탭에도 즉시 전파해 남은 AT를 정리한다.
- 요청 본문과 성공 응답 계약, DB 스키마는 유지했다. MCP에 등록된 인증 갱신 도구가 없어 `register-tools.ts` 변경은 필요하지 않았다.

- 로컬 실행 환경에는 Chrome 151과 Edge 151이 설치되어 있지만 Playwright·Puppeteer·Selenium 및 전용 드라이버는 설치되어 있지 않다.

- 안전한 쿠키 이전 순서는 `Origin 방어 → 서버 dual-read/dual-issue → 브라우저 쿠키 사용 전환 → 안정화 확인 → 응답 body와 Web Storage RT 제거`의 단계 배포가 적합하다. 한 번에 전환하지 않는다.

### 2026-08-20 — SEC-017 Refresh Token 30일 절대 수명 적용

- 사용자 결정에 따라 로그인 세션의 Refresh Token 정책을 `마지막 갱신 후 10일 유휴 만료 + 최초 로그인 후 30일 절대 만료`로 확정했다.
- 새 RT의 만료 시각은 `MIN(갱신 시각 + 10일, tb_cm_member_session.creat_dt + 30일)`로 계산한다. 로그인 유지 미선택 세션은 브라우저 세션 종료 시 더 일찍 끝나며, 서버의 30일 상한은 모든 로그인 세션에 동일하게 적용한다.
- 30일 절대 만료 시각 이후에는 기존 RT의 자체 만료일이 남아 있어도 회전을 거부하고 기존 `401 INVALID_TOKEN` 계약으로 재로그인을 요구한다.
- 30일 직전에 발급한 30분 Access Token이 절대 만료 시각을 넘기지 않도록, 마지막 구간의 JWT `exp`도 세션 절대 만료 시각으로 제한했다.
- DB 스키마나 요청·성공 응답 형식은 변경하지 않고 기존 세션 `creat_dt`를 사용했다. 인증 갱신 MCP 도구가 없으므로 `register-tools.ts` 변경은 필요하지 않았다.
- UW-00002 로그인 PRD에 10일/30일 정책과 만료 처리를 반영했다. 이 단계에서는 UW-00004 JWT PRD를 당시 구현인 `AT 30분·Web Storage·원자적 RT 회전` 기준으로 먼저 바로잡았고, 이후 아래 HttpOnly 전환 절에서 최종 쿠키 방식으로 다시 갱신했다.
- 사전 읽기 전용 확인에서 활성·미만료 RT가 연결된 세션은 모두 생성 후 10일 이내였으므로 배포 즉시 30일 상한으로 끊기는 현재 사용자는 없다.
- 순수 함수 경계 테스트로 10일 연장, 30일 상한, 정확한 30일 경계 거부, 마지막 Access Token 상한을 검증했다.
- 임시 PostgreSQL 스키마에서는 생성 후 25일인 세션의 동시 RT 회전을 실행해 성공 1건·충돌 1건·활성 새 RT 1건과 새 RT 만료일이 정확히 세션 생성 후 30일로 저장되는 것을 확인한 뒤 스키마를 삭제했다.

### 2026-08-20 — SEC-017 Refresh Token HttpOnly 쿠키 전환

- 사용자 승인에 따라 JavaScript가 읽을 수 있던 Web Storage RT를 `HttpOnly; SameSite=Strict; Path=/` 쿠키로 전환했다. 운영 쿠키는 `__Host-specode_rt` 이름과 `Secure` 속성을 강제하며, 개발 환경만 localhost HTTP 검증을 위해 비-Secure 이름을 사용한다.
- 자동 로그인 선택 시 쿠키에 RT 만료 시각을 설정하고, 미선택 시 브라우저 종료와 함께 사라지는 세션 쿠키로 설정한다. 서버의 10일 유휴·30일 절대 만료 정책은 그대로 유지한다.
- 로그인·가입 완료·기존/신규 소셜 로그인·소셜 연동·RT 회전의 모든 발급 경로가 쿠키를 설정하며, 로그아웃·회원 탈퇴·인증 실패는 쿠키를 명시적으로 만료시킨다.
- 새 클라이언트는 `x-specode-auth-mode: cookie`를 보내고 응답 본문에서는 AT만 받는다. 쿠키를 사용해 인증한 요청에는 요청 헤더 유무와 관계없이 RT 원문을 절대 반환하지 않는다.
- 배포 전 브라우저에 남은 RT는 최초 갱신 body로 한 번 제출해 새 쿠키로 회전하고 성공 즉시 local/sessionStorage에서 삭제한다. 기존 클라이언트는 자신이 보유한 body RT를 제출한 경우에만 전환 기간 동안 새 RT 본문을 받을 수 있다.
- 클라이언트 다중 탭 프로토콜을 v2로 바꿔 탭 사이에는 AT만 전달하고 RT 원문·지문은 전달하지 않는다. HttpOnly 쿠키는 브라우저가 탭 간 공유하고 Web Lock과 서버 CAS가 갱신을 직렬화한다.
- 새 탭에 AT가 없어도 MainLayout이 HttpOnly 쿠키로 AT를 복원하며, 기존 Web Storage RT가 발견되면 화면을 막지 않고 백그라운드 승계를 수행한다.
- 쿠키를 사용하는 갱신·로그아웃 요청은 정확한 Origin과 Sec-Fetch-Site 동일 출처 여부를 검사한다. 로그인·가입·소셜 발급 경로도 교차 출처 Origin을 거부한다.
- 비밀번호 변경은 더 이상 클라이언트 RT를 받지 않고, Access Token의 `sesnId`와 실제 DB의 활성 세션·ACTIVE 회원 상태를 함께 확인해 나머지 RT와 세션만 무효화한다. 기존 회원 조회를 관계 조회로 대체해 쿼리 수는 늘리지 않았다.
- 현재 웹 클라이언트의 성공 응답에서 RT 필드를 제거했으므로 UW-00001/00002/00003/00004/00006 PRD를 함께 갱신했다. 인증 API는 MCP 도구로 등록되어 있지 않아 `register-tools.ts` 변경 대상은 없다.
- 순수 정책 테스트로 쿠키/body 자격 증명 우선순위, 쿠키 응답의 RT 비노출, 쿠키 속성, 정확한 Origin, 기존 Web Storage 정리를 검증했다.
- 별도 임시 PostgreSQL 스키마에서 실제 route 함수를 실행해 쿠키 로그인·교차 출처 403·원자적 회전·현재 세션 보존 비밀번호 변경·로그아웃 쿠키 삭제·기존 body RT 쿠키 승계를 모두 확인하고 스키마를 삭제했다.

## 남은 위험 항목

### 즉시 운영 조치가 필요한 항목

- SEC-001 원문 MCP 키: 사용자가 추후 직접 폐기하기로 결정해 이번 작업에서는 키·추적 파일·Git 이력을 변경하지 않았다.
- 의존성 취약점: 인증 변경과 분리한 전용 업그레이드 작업에서 Next.js 동일 minor의 최신 patch부터 단계적으로 적용하고, 시각 편집기·Mermaid·메일·이미지 처리 실제 동작까지 검증해야 한다.

### 설계 또는 동시성 검증이 먼저 필요한 항목

- HttpOnly 전환 호환 코드 정리: 실제 배포 후 기존 탭의 승계 기간을 확인한 다음 body RT 입력·응답과 Web Storage 호환 함수를 제거해야 한다. 현재 쿠키 인증 경로에서는 호환 코드로 RT를 꺼낼 수 없다.
- 모든 JWT 요청의 세션 실시간 조회: 현재 측정 지연(p95 약 984ms) 때문에 전역 적용하지 않았다. 고위험 API 선별 또는 캐시/토큰 버전 설계가 필요하다.
- SEC-003/007/013/015: 프로젝트 소유권·탈퇴·초대·일회용 토큰의 트랜잭션/불변식 변경은 운영 데이터 형태와 경쟁 요청 통합 테스트가 필요하다.
- SEC-005/006/009/010/011/016/018~022: HTML 정화, 테넌트 경계, 저장소, AI 실행, entitlement, 이메일 정규화, 운영 통제는 여러 화면/API/데이터 계약에 걸쳐 있어 항목별 PRD 대조와 전용 회귀 테스트 후 분리 적용해야 한다.
