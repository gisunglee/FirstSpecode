## 2. 화면별 분석

### 대시보드 (`/dashboard`)
- **역할**: 로그인 후 기본 진입 화면. 시간대 인사 + "관리뷰/개발자뷰" 토글 + 카드 3개.
- **누구에게**: 처음 들어온 모든 사용자 — 랜딩 페이지 성격.
- **실효성**: 역할별로 다른 카드(관리자=진행률/정체/최근변경, 개발자=내 과업/마감/AI결과)를 보여주는 건 합리적. 다만 "개발자뷰" 3카드(내 과업·내 마감·내 AI결과)가 아래 **My Task / MY 보드 / 캘린더**와 내용이 겹친다.

### PM 진단 (`/pm`, 구 "PM 워치")
- **역할**: 걱정되는 지점이 있을 때 파고드는 "사람 기준" 정밀 진단 — 팀 부하 매트릭스, 미지정/분석 현황, 설계·구현 지연, 마감×진척 히트맵, 마감임박 리스트(단위업무/화면/기능).
- **누구에게**: PM/팀장. "어디가 문제인지 자세히 보고 싶을 때" 들어오는 화면.
- **실효성**: 위젯이 6개 이상 세로로 쌓여 화면이 길다 — 매일 보기보단 문제 진단용으로 적합. ~~"위험 워치리스트/우선순위 히트맵"을 대체하고 남아있던 죽은 코드~~ → **RiskWatchlist.tsx, PriorityHeatmap.tsx 및 `pm-summary` API의 `riskItems`/`priorityMatrix` 계산 삭제 완료(2026-07-20)**.

### PM 현황 (`/pm-board`, 구 "PM 보드")
- **역할**: 매일 가볍게 훑어보는 "항목 기준" 전체 목록 — 요구사항분석/단위업무·화면·기능×설계·구현 = 7개 카테고리 카드, 카드마다 4구간 도넛 + 마감임박 표.
- **누구에게**: PM. "대충 잘 돌아가네"를 1~2일 주기로 빠르게 확인하려는 용도.
- **실효성**: PM 진단(문제 있을 때 깊게 보기) vs PM 현황(매일 가볍게 훑기)으로 이름과 실제 용도가 일치하게 됨(2026-07-20 개명). 단, "MY 보드"라는 이름이 원래 "PM 보드"와 짝을 이루도록 지어졌던 것이라(코드 주석 확인), 이번 개명으로 그 짝이 깨졌음 — MY 보드도 함께 바꿀지 별도 결정 필요.

### 활동 (`/activity`)
- **역할**: 최근 변경/검토/AI완료 이벤트를 시간순 피드로. 기간필터+무한스크롤.
- **누구에게**: 프로젝트 전체 흐름을 훑고 싶은 모든 멤버.
- **실효성**: 카드형 대시보드들과 패러다임이 달라(단일 스트림) 대체 불가능한 고유 기능. 유지 권장.

### 포커스 (`/focus`)
- **역할**: "오늘 1순위 1건"을 크게, 다음 후보 2건을 작게. 우선순위는 `lib/focus/prioritize.ts` 순수 함수로 산정.
- **누구에게**: 실무자(개발자/디자이너) 개인 — "오늘 뭐부터 하지"에 대한 답.
- **실효성**: 컨셉은 명확하고 좋음. 문제는 **My Task/MY 보드가 이미 마감일순 정렬 리스트를 제공**해서, 포커스가 주는 추가 가치는 "1건으로 압축"뿐. 우선순위 산정 로직이 신뢰할 만하면 가치 있고, 아니면 그냥 My Task 정렬 상단과 다를 게 없어짐.

### MY 보드 (`/my-work`)
- **역할**: 내가 담당한 요구사항/단위업무/화면/기능 전체 + 그 하위의 담당자 미지정 항목까지 한 스냅샷. 기준일을 앞당겨 "내일이면?" 시뮬레이션 가능.
- **누구에게**: 실무자 개인.
- **실효성**: "미지정 하위 항목"까지 보여주는 건 실무자가 놓치기 쉬운 부분을 잡아주는 좋은 설계. 다만 **My Task와 대상 범위가 거의 동일**(단위업무/화면/기능, 담당자=나로 필터한 My Task와 사실상 같은 결과 집합).

### My Task (`/my-task`)
- **역할**: 단위업무/화면/기능을 팀 전체 기준으로 조회, 담당자 필터 변경 가능, 목록/그룹(트리) 전환, 담당자·일정·공수 인라인 편집.
- **누구에게**: PM(남의 일정도 조정) + 실무자(내 일 인라인 수정) 둘 다.
- **실효성**: 가장 실무 활용도가 높은 화면 — 조회+편집이 한 곳에서 됨. **다만 담당자 필터에서 "전체"를 풀면 사실상 PM 진단/PM 현황이 하는 일(팀 전체 현황)까지 겹침.** 이 화면 하나에 편집 권한까지 있다는 게 핵심 차별점이므로, 다른 조회 전용 화면들과의 역할 분담을 명확히 문서화할 필요.

### 캘린더 (`/calendar`)
- **역할**: 단위업무 종료일을 월간 그리드에 표시. "내 담당만" 필터.
- **누구에게**: 일정을 달력 형태로 보고 싶은 모든 사용자.
- **실효성**: 대상이 **단위업무 종료일 뿐**(화면/기능 제외) — WBS/My Task는 3종을 다 다루는데 캘린더만 범위가 좁음. 월간 뷰라는 표현 형식 자체는 리스트/간트와 확실히 달라 존재 가치는 있으나, 화면/기능도 넣어야 "일정 캘린더"로서 완결성이 생김.

### WBS 일정 (`/wbs`, 별도 그룹)
- **역할**: 단위업무/화면/기능 3종 간트차트. 담당자 필터, 목록/그룹 보기, 바 표시옵션, 상태색상, 압축모드, 페이징.
- **누구에게**: 일정을 시각적(간트)으로 보고 싶은 PM/실무자.
- **실효성**: 옵션이 풍부하고 3종 통합 조회라 완성도 높음. 영역(Area)은 날짜 컬럼이 없어 제외됐다고 명시 — 의도된 제한이라 문제 아님.

## 3. 핵심 문제: "내 할 일 보기"가 5개나 있음

| 화면 | 관점 | 편집 가능 | 표시 형식|
|---|---|---|---|
| 대시보드(개발자뷰) | 나 | ✗ | 카드 3개 요약 |
| MY 보드 | 나 (+ 하위 미지정) | ✗ | 요약 + 리스트 |
| My Task (담당자=나) | 나 | ✓ | 목록/트리 |
| 포커스 | 나 (1건 압축) | ✗ | 카드 |
| 캘린더 (내 담당만) | 나 (일정만) | ✗ | 월간 그리드 |

다섯 화면 모두 "로그인한 나의 담당 업무"라는 같은 소스 데이터를 다른 표현 형식으로 반복 제공한다. 각각 코드 주석에는 "다른 화면과 컨셉이 다르다"는 차별화 근거가 적혀 있지만, **실제 사용자 입장에서는 어느 화면이 1차 진입점인지 알기 어렵고, 메뉴가 8개나 되어 신규 사용자의 학습 비용이 크다.**

**개선 방향 제안**
1. **압축**: 대시보드(개발자뷰)의 "내 과업/마감" 카드는 My Task·MY 보드와 중복이므로, 대시보드는 랜딩/알림 요약 역할만 남기고 상세는 링크로 연결.
2. **포커스 재검토**: 우선순위 알고리즘에 확신이 없다면 유지보수 부담 대비 가치가 낮음 — My Task 정렬(마감일순) 최상단 강조 UI로 대체 검토.
3. **캘린더 범위 확장**: 화면/기능도 포함해 WBS와 동일한 3종 커버리지로 맞추거나, 아니면 "캘린더는 단위업무 전용"임을 메뉴 라벨에 명시.
4. ~~**PM 워치 ↔ PM 보드 네이밍 재정비**~~ → **완료(2026-07-20)**: "PM 워치"→"PM 진단"(문제 있을 때 깊게 파고드는 화면), "PM 보드"→"PM 현황"(매일 가볍게 훑는 목록 화면)으로 개명. LNB·페이지 타이틀·API 에러 메시지·관련 주석까지 일괄 반영.
