# SPECODE 전체 보안 감사 보고서

- 감사 기준일: 2026-08-20 (Asia/Seoul)
- 대상: 현재 워크스페이스의 SPECODE 애플리케이션, API, MCP, AI 워커/커맨드, DB 스키마·DDL, 파일 저장, 인증·권한, 배포 관련 설정
- 검토 규모: Git 추적 파일 938개, API Route Handler 286개, HTTP MCP 도구 50개
- 감사 방식: 정적 소스 검토, 권한·테넌트 경계 추적, 주요 공격 경로 수동 재구성, 로컬 테스트 및 설정 검증
- 결론: **현재 상태로 유료 다중 테넌트 공개 서비스 배포는 No-Go**

> 이 보고서는 위험을 과장하지 않기 위해 `확정 취약점`, `조건부 위험`, `개선 권고`, `이미 양호한 통제`를 구분한다. 실제 클라우드 계정, 운영 DB, 프록시/WAF, DNS/TLS, 백업, CI 비밀 저장소에는 접속하지 않았으므로 그 상태는 별도 검증이 필요하다.

가장 현실적인 공격 연결 고리는 다음 세 가지다.

1. **Git에 포함된 MCP 키 → 일반 회원 API 호출 → 계정 탈취**  
   저장소에 원문 `spk_...` 키가 4개 존재하고, CLIENT MCP 키가 프로젝트 API뿐 아니라 이메일 변경, 소셜 연동, 비밀번호 설정, 새 MCP 키 발급에도 사용될 수 있다.
2. **일반 멤버/뷰어 → 리뷰 권한 판정 반전 → 악성 HTML 저장 → 다른 사용자의 브라우저 세션 탈취**  
   `checkRole()` 반환값을 boolean으로 반대로 해석하고 있으며, 리뷰 화면은 저장된 HTML을 정화 없이 삽입한다. 브라우저 토큰도 Web Storage에 있어 XSS 영향이 커진다.
3. **계정 탈퇴 → 과거에 생성했지만 이미 소유권을 넘긴 프로젝트까지 즉시 물리 삭제**  
   현재 OWNER가 아니라 `creat_mber_id`를 기준으로 프로젝트를 삭제한다. 정상 프로젝트 삭제의 14일 복구 절차도 우회한다.

## 2. 즉시 해야 할 조치 — 24시간 이내

1. **노출된 MCP 키 4개를 전부 폐기하고 새로 발급한다.** 키의 유효성을 시험하지 말고 노출된 것으로 간주한다.
2. `.mcp.json`, `.codex/config.toml`, `.claude/settings.local.json`에서 원문 키를 제거하고 Git 추적을 해제한다. 현재 브랜치만 고치는 것으로 끝내지 말고 전체 Git 이력을 비밀 스캐너로 조사한 뒤 이력 정리 여부를 결정한다.
3. 임시 핫픽스로 `spk_` 인증을 `/api/mcp`, 프로젝트 범위 API, `/api/worker`의 의도된 채널 외에서는 거부한다. 특히 `/api/auth/mcp-keys/**`, `/api/member/**`는 세션 JWT만 허용한다.
4. 회원 탈퇴 API에서 프로젝트 물리 삭제 코드를 비활성화하고, 현재 OWNER 멤버십을 기준으로 사전 검증하도록 바꾼다.
5. 리뷰 수정·삭제 및 코멘트 수정·삭제를 일시적으로 막거나 `requirePermission()` 기반으로 즉시 교체한다.
6. 정화 레이어가 배포될 때까지 사용자/AI 생성 HTML과 Markdown의 `dangerouslySetInnerHTML` 렌더링을 비활성화하거나 plain text로 표시한다.
7. 아래 SEC-006의 테넌트 경계 누락 라우트와 `/api/diff-test/**`를 운영에서 차단한다.

## 3. 상세 발견 사항

### SEC-001 — Git 추적 파일에 원문 MCP Bearer 키 존재

- 심각도: **Critical**
- 상태: **확정**
- 근거:
  - `.mcp.json:8` — 운영 URL `https://www.specode.co.kr/api/mcp`와 원문 Bearer 키
  - `.codex/config.toml:5` — 원문 Bearer 키
  - `.claude/settings.local.json:247-274,324,327` — 여러 curl 명령 안의 원문 CLIENT/WORKER 키
  - 현재 추적 내용에서 서로 다른 `spk_` 키 **4개** 확인
  - `.gitignore:32-35`는 `.mcp.json`을 제외하도록 되어 있지만 이미 Git에 추적된 파일에는 효력이 없다. 나머지 두 파일에 대한 제외 규칙도 없다.
- 영향:
  - 저장소 접근자, CI 로그·캐시, 코드 백업, 유출된 Git 이력이 키를 재사용할 수 있다.
  - 프로젝트 조회·수정, AI 태스크, 워커 실행이 가능하고 SEC-002 때문에 계정 영역까지 확대될 수 있다.
- 과장하지 않은 판단:
  - 키가 이미 폐기됐는지는 확인하지 않았다. 그러나 원문 비밀이 Git에 들어간 사실 자체는 확정이며, `.mcp.json`은 운영 엔드포인트를 가리킨다.
- 조치:
  - 키 4개 즉시 폐기·재발급, 키 사용 로그 조사, 영향받은 프로젝트 변경 이력 확인.
  - `git rm --cached`에 해당하는 추적 해제 후 로컬 전용 템플릿만 유지.
  - Gitleaks/TruffleHog 같은 pre-commit·CI 비밀 스캔과 Git 호스팅 push protection 적용.
  - MCP 키에 만료일, 마지막 IP/UA, per-key 감사 로그, 자동 회전 기능 추가.

### SEC-002 — 프로젝트용 MCP 키가 계정 인증 수단으로 승격됨

- 심각도: **Critical**
- 상태: **확정**
- 근거:
  - `src/lib/requireAuth.ts:91-157`은 CLIENT `spk_` 키를 JWT와 같은 `AuthPayload`로 반환한다.
  - MCP 키 인증 시 키 소유 회원의 `mber_sttus_code`도 확인하지 않아 정지·탈퇴 상태를 자격증명 단계에서 차단하지 않는다(`requireAuth.ts:105-113`).
  - URL scope 검사는 `/api/projects/[id]/**`에만 적용되고 프로젝트 밖 경로는 통과한다(`requireAuth.ts:42-78`).
  - MCP 키 관리 GET/POST/DELETE가 모두 `requireAuth()`만 사용한다(`src/app/api/auth/mcp-keys/route.ts:42-44,98-100`, `[keyId]/route.ts:19-21`).
  - 키 생성 시 요청된 `prjctId`의 멤버십은 확인하지만 현재 API 키의 `allowedPrjctId`와 대조하지 않는다(`mcp-keys/route.ts:150-173`). 프로젝트 A 키 하나로 사용자가 속한 프로젝트 B용 새 키를 발급할 수 있어 원래 scope를 우회한다. GET은 사용자의 전체 키 목록을 보여주고 DELETE는 다른 프로젝트 키도 폐기할 수 있다.
  - `/api/projects`는 URL scope 예외인데 POST 생성 경로는 `allowedPrjctId`를 검사하지 않는다(`src/app/api/projects/route.ts:33-104`). 프로젝트 전용 키로 새 프로젝트와 OWNER 멤버십을 만들 수 있다.
  - 이메일 변경도 `requireAuth()`만 사용하고 현재 비밀번호나 최근 재인증이 없다(`src/app/api/member/profile/email/change/route.ts:22-24`). 새 주소로 온 링크를 열면 인증 없이 이메일이 바뀐다(`email/complete/route.ts:17-87`).
  - 더 심각하게 `/api/auth/verify`는 `vrfctn_ty_code === 'REGISTER'`를 검사하지 않는다. 따라서 `EMAIL_CHANGE` 토큰도 회원을 ACTIVE로 만들고 새 AT/RT 세션으로 교환된다(`src/app/api/auth/verify/route.ts:36-55,68-103`).
  - 소셜 전용 계정은 현재 비밀번호 없이 새 비밀번호를 설정할 수 있다(`profile/password/route.ts:43-63`).
  - 소셜 계정 추가·해제도 API 키를 세션 JWT처럼 받아들인다(`member/social/link/route.ts:20-22`, `social/unlink/route.ts:17-19`).
  - 회원 탈퇴도 같은 문제가 있고 소셜 전용 계정은 `socialToken` 없이 통과하는 분기가 있다(`member/me/route.ts:64-89`).
- 실제 공격 경로:
  1. 프로젝트 범위 CLIENT 키를 획득한다.
  2. 피해자 명의로 새 CLIENT/WORKER 키를 발급해 지속성을 만든다. 피해자가 다른 프로젝트의 멤버라면 그 프로젝트용 키도 발급해 단일 프로젝트 scope를 횡단한다.
  3. 공격자 이메일로 이메일 변경을 요청한 뒤 받은 `EMAIL_CHANGE` 토큰을 `/api/auth/verify`에 제출해 즉시 로그인 세션을 받거나, 공격자 소셜 계정을 피해자 계정에 연동하거나, `pswd_hash=null` 계정에 비밀번호를 설정한다.
  4. 정상 로그인 수단을 얻고 기존 키를 폐기해 피해자의 대응을 방해할 수 있다.
- 조치:
  - 인증 결과에 `credentialType: SESSION | MCP_CLIENT | WORKER`와 capability를 명시하고 기본 거부한다.
  - 계정·자격증명·결제·관리 API는 **활성 세션 JWT + 최근 재인증**만 허용한다.
  - 모든 일회용 토큰 소비 API에서 토큰의 대상 회원뿐 아니라 정확한 `token type/purpose`, 상태, 만료를 원자적으로 검증한다.
  - CLIENT 키는 MCP 도구 allowlist 또는 프로젝트 리소스 API에만 허용하고, 키가 다른 키를 발급·폐기할 수 없게 한다.
  - 이메일/비밀번호/소셜 변경 시 기존 세션과 관련 키를 재평가·폐기하고 보안 알림을 보낸다.

### SEC-003 — 회원 탈퇴가 양도 완료 프로젝트까지 즉시 물리 삭제

- 심각도: **Critical**
- 상태: **확정**
- 근거:
  - 탈퇴 API가 `creat_mber_id === auth.mberId`인 프로젝트를 전부 찾고 멤버와 프로젝트를 `deleteMany()` 한다(`src/app/api/member/me/route.ts:93-116`).
  - `creat_mber_id`는 생성자이지 현재 OWNER 멤버십이 아니다. 소유권을 넘겨도 생성자는 바뀌지 않는다.
  - 정상 프로젝트 삭제는 OWNER, `confirm:'DELETE'`, 기본 14일 soft-delete와 복구 절차를 거친다(`projects/[id]/route.ts:252-381`). 탈퇴 경로는 이를 모두 우회한다.
- 영향:
  - 프로젝트를 만든 사람이 소유권을 양도한 뒤 계정을 탈퇴하면 새 OWNER와 전체 고객 데이터가 즉시 사라질 수 있다.
  - SEC-002의 탈취 경로가 소셜 전용 계정에 도달하면 공격자가 이 파괴 동작을 수행할 수 있다.
- 조치:
  - 회원 탈퇴에서 프로젝트 직접 삭제를 제거한다.
  - 현재 `ACTIVE + OWNER` 멤버십이 하나라도 있으면 양도/보관/삭제 선택을 완료하기 전 탈퇴를 거부한다.
  - 삭제가 선택되더라도 기존 프로젝트 soft-delete 워크플로만 호출하고 비동기 정리한다.
  - 최근 재인증, 감사 로그, 재확인 토큰, 관리자·소유자 알림을 필수화한다.

### SEC-004 — 리뷰의 관리자 판정이 반대로 동작해 권한 우회

- 심각도: **Critical**
- 상태: **확정**
- 근거:
  - `checkRole()`은 허용 시 `null`, 거부 시 `403 Response`를 반환한다(`src/lib/checkRole.ts:34-48`).
  - 리뷰 라우트는 이를 `const isAdmin = checkRole(...)`로 받은 뒤 boolean처럼 사용한다(`reviews/[reviewId]/route.ts:95-107,129-155,203-216`).
  - 따라서 OWNER/ADMIN은 `null`이라 비관리자로 처리되고, MEMBER/VIEWER는 `Response` 객체가 truthy라 관리자로 처리된다.
  - 코멘트 DELETE도 같은 반전이 있다(`comments/[commentId]/route.ts:86-89`).
- 영향:
  - 같은 프로젝트의 일반 멤버·뷰어가 요청자/답변자 제한, 상태 허용값, 만족도 범위, 코멘트 유무 제한을 우회해 리뷰를 수정·삭제할 수 있다.
  - 코멘트의 프로젝트 상위 검증 누락과 결합하면 다른 프로젝트 코멘트 삭제도 가능하다.
  - SEC-005와 결합해 VIEWER가 저장형 XSS 페이로드를 기록할 수 있다.
- 조치:
  - `checkRole()`을 이 라우트에서 제거하고 `requirePermission()` 및 명시적인 `gate.role === 'OWNER' || gate.role === 'ADMIN'`으로 교체한다.
  - 반환형이 `Response | null`인 함수를 boolean 변수에 대입하지 못하도록 ESLint/타입 래퍼를 추가한다.
  - 역할별 API 통합 테스트를 OWNER/ADMIN/MEMBER/VIEWER 전부에 대해 작성한다.

### SEC-005 — 사용자·AI 콘텐츠의 저장형 XSS

- 심각도: **Critical**
- 상태: **확정**
- 근거:
  - 리뷰 요청·답변·코멘트를 정화 없이 직접 `dangerouslySetInnerHTML`로 삽입한다(`reviews/[reviewId]/page.tsx:386-390,432-436,548-552`).
  - 공통 Markdown 렌더러가 `marked.parse()` 결과를 sanitize하지 않으며 주석도 내부 도구라는 가정을 명시한다(`src/lib/renderMarkdown.ts:13-16,35-53`). 유료 다중 사용자 서비스에서는 성립하지 않는 가정이다.
  - 동일 패턴이 MarkdownEditor, DesignExamplePopup, ImplRequestPopup, 기능 상세, 플랜 스튜디오, 설계 변경 등에 걸쳐 9개 파일에서 사용된다.
  - 로컬 PoC에서 `marked.parse('<img src=x onerror=...>')`와 `<svg onload=...>` 이벤트 속성이 그대로 출력됨을 확인했다.
  - CSP가 `script-src 'self' 'unsafe-inline'`을 허용한다(`src/lib/securityHeaders.ts:31-41`). Web Storage의 AT/RT도 스크립트에서 읽을 수 있다(`src/lib/authFetch.ts:44-46,67-75,186-212`).
- 영향:
  - 악성 콘텐츠를 다른 프로젝트 멤버가 열면 동일 오리진에서 API 호출, 설계 변조, 이메일 변경, 토큰 탈취 등이 가능하다.
  - `connect-src 'self'`는 외부 fetch 유출을 줄이지만 동일 오리진 악용, 폼/탐색 기반 유출, 계정 설정 변경을 막지 못한다.
- 조치:
  - 저장 시와 렌더링 시 모두 HTML allowlist 정화 적용. 이벤트 속성, `script`, 위험한 SVG, `javascript:` URL, iframe/object를 제거한다.
  - Markdown은 `rehype-sanitize` 계열처럼 Markdown AST 단계에서 정화하고, RichEditor HTML은 별도 스키마를 사용한다.
  - CSP nonce/hash와 Trusted Types를 단계적으로 적용하고 `unsafe-inline`을 제거한다.
  - 보안 회귀 테스트에 `<img onerror>`, SVG, `javascript:` 링크, malformed HTML을 포함한다.

### SEC-006 — 여러 API에서 프로젝트 상위 관계 검증 누락(IDOR/BOLA)

- 심각도: **High**
- 상태: **확정**

  - 탈퇴 계정도 로그인 후 `requireAuth()`만 쓰는 프로젝트 생성 API로 새 프로젝트와 ACTIVE OWNER 멤버십을 만들 수 있다(`src/app/api/projects/route.ts:33-104`).

- 조치:
  - 로그인·refresh·MCP 인증 단계에서 허용 상태를 명시적으로 allowlist하고, 일반 API도 회원 ACTIVE 여부를 공통 검증한다.

  - RT는 `HttpOnly; Secure; SameSite` 쿠키로 옮기고 AT는 메모리 보관을 우선한다. 쿠키 전환 시 CSRF 토큰/Origin 검사를 함께 설계한다.
  - 이메일·비밀번호·시스템 역할 변경 시 모든 세션/키를 정책에 따라 폐기한다.
  - SUPER_ADMIN에는 MFA/패스키와 짧은 step-up 인증을 적용한다.

  - `/api/diff-test/save|diff|list|load|load-latest|reset` 6개 라우트에 인증·환경 게이트가 없다.
  - reset은 테이블 전체를 삭제한다(`src/app/api/diff-test/reset/route.ts:12-18`).
  - save는 입력 크기 제한 없이 raw Markdown을 DB에 저장한다(`diff-test/save/route.ts:22-35,107-123`).
  - `src/app/test/diff-prompt/page.tsx`도 일반 앱 트리에 있다.
- 과장하지 않은 판단:
  - 고객 본 테이블이 아니라 diff-test 전용 데이터가 직접 영향받는다. 다만 무인 DB/CPU/저장소 남용 경로이므로 운영 노출은 부적절하다.
- 조치: production 빌드에서 제거하거나 SUPER_ADMIN/dev-only gate, 크기·rate limit을 적용한다.

### SEC-015 — 이메일 열거·재발송 남용과 평문 일회용 토큰

- 심각도: **Medium**
- 상태: **확정**
- 근거:
  - `/api/auth/email/check`가 계정 존재 여부를 직접 반환하고 rate limit이 없다(`email/check/route.ts:15-28`).
  - 가입 인증 재발송과 잠금 해제 재발송은 존재·상태를 구분하고 rate limit 없이 이메일을 보낸다(`email/resend/route.ts:20-79`, `unlock/email/resend/route.ts:17-69`).
  - 인증/이메일 변경/잠금 해제/초대 토큰은 DB에 원문 저장된다. DB read 유출 시 토큰 만료 전 계정 작업에 사용할 수 있다.
  - 가입 인증과 비밀번호 재설정은 PENDING을 먼저 읽은 뒤 조건 없는 update를 하므로 동시 요청에서 같은 토큰이 둘 다 사전 검증을 통과할 수 있다(`auth/verify/route.ts:36-78`, `auth/password/reset/route.ts:84-117`).
  - SMTP 미설정 시 인증·변경·재설정 링크를 환경 구분 없이 콘솔에 출력한다(`src/lib/auth.ts:174-189,225-238,271-283`). 운영 오설정 시 bearer 링크가 로그에 남고 API는 성공처럼 동작한다.
- 조치:
  - 응답 균질화, IP+이메일+계정 rate limit, 발송 cooldown·일일 한도·CAPTCHA 위험 기반 적용.
  - 일회용 토큰을 SHA-256 해시로 저장하고 `purpose + PENDING + expiry` 조건부 update의 영향 행 수 1로 단일 소비를 보장.
  - production SMTP 미설정은 fail-fast하고 링크/토큰 로그를 금지한다.

### SEC-016 — OAuth 후 redirect 검증 부재와 이메일 정규화 부재

- 심각도: **Medium (조건부)**
- 상태: **소스상 검증 부재 확정**, 외부 이동 동작은 프레임워크 런타임 회귀 테스트 필요
- 근거:
  - 로그인 페이지가 `redirect` 값을 검증 없이 `router.replace()`에 넘긴다(`src/app/(auth)/auth/login/page.tsx:53,90,121`).
  - OAuth state에 redirect 문자열을 직접 넣고 callback이 다시 반환한다(`auth/social/[provider]/authorize/route.ts:35-45`, `auth/social/callback/route.ts:50`).
  - `//attacker.example` 같은 protocol-relative 값이나 역슬래시·제어문자를 거부하는 코드가 없다.
  - 이메일 비교·저장이 일관되게 lower-case/trim 정규화되지 않아 대소문자 변형 계정과 초대 바인딩 혼란이 가능하다.
- 조치:
  - redirect는 단일 `/`로 시작하고 `//`, `\\`, 제어문자, scheme을 포함하지 않는 same-origin path만 허용한다.
  - OAuth state는 서명된 구조화 JSON/base64url로 만들고 nonce와 목적·redirect를 검증한다.
  - 이메일 canonicalization 정책을 정하고 DB unique 인덱스도 `lower(email_addr)` 기준으로 이관한다.

### SEC-017 — Refresh Token 회전 경쟁과 JWT 검증 제약 부족

- 심각도: **Medium**
- 상태: **확정**
- 근거:
  - refresh가 active 토큰을 읽은 후 조건 없는 update+create를 수행한다(`auth/token/refresh/route.ts:63-79,112-144`). 동시 두 요청이 둘 다 폐기 전 상태를 읽으면 새 RT가 두 개 발급될 수 있다.
  - JWT sign/verify에 algorithm allowlist, issuer, audience가 명시되지 않는다(`src/lib/auth.ts:76-87,143-163`). 현재 jsonwebtoken 기본 동작으로 서명 검증은 되지만 서비스 경계가 명시적이지 않다.
- 조치:
  - `revoked_dt IS NULL` 조건부 `updateMany` 결과가 1인 요청만 새 토큰을 발급하거나 row lock을 사용한다.
  - 토큰 family/replaced-by를 기록하고 family reuse를 원자적으로 탐지한다.
  - `algorithms: ['HS256']`, `issuer`, `audience`, token type, `jti`를 명시한다.

### SEC-018 — 감사·탐지·고권한 인증 통제가 부분적

- 심각도: **Medium**
- 상태: **확정 범위 부족**
- 양호한 부분:
  - 시스템 역할 임명/해임은 이유를 요구하고 같은 트랜잭션에 감사 로그를 남긴다(`admin/users/[id]/system-role/route.ts:97-133`).
  - 지원 세션과 프로젝트 hard delete도 감사 대상이다.
- 부족한 부분:
  - MCP 키 발급·폐기·도구 호출, 이메일/비밀번호/소셜 변경, 프로젝트 역할 변경·제거, 초대 수락, 리뷰·artifact 삭제 등의 중앙 보안 감사가 없다.
  - `last_used_dt`는 fire-and-forget이고 도구명·결과·IP/UA가 남지 않는다.
  - SUPER_ADMIN MFA, 위험 작업 step-up, 이상 징후 경보, CSP report endpoint, Sentry/OTel 연동 근거가 저장소에서 확인되지 않는다.
- 조치:
  - immutable/append-only 감사 이벤트에 actor, credential ID/type, tenant, action, target, result, IP/UA, correlation ID를 저장한다. 비밀과 원문 콘텐츠는 기록하지 않는다.
  - 계정 보안·관리자·키·교차 테넌트 거부·대량 export·AI 비용 폭증을 실시간 경보한다.

### SEC-019 — DB 최소권한·RLS·무결성 방어가 저장소에서 확인되지 않음

- 심각도: **Medium**
- 상태: **방어 계층 미확인. 애플리케이션 IDOR는 별도로 확정**
- 근거:
  - `.env.local.example:3-6`은 애플리케이션과 direct migration 모두 `postgres` 역할 예시다.
  - 스키마·SQL에서 tenant RLS policy, 전용 app role, role/job/plan 상태 CHECK 제약을 확인하지 못했다.
  - review comment와 다형 참조/매핑 구조는 프로젝트 FK가 약해 SEC-006 같은 실수를 DB가 막지 못한다.
- 과장하지 않은 판단:
  - RLS가 없다고 무조건 취약한 것은 아니다. 그러나 이미 앱 계층 IDOR가 발견됐으므로 두 번째 방어선의 가치가 크다. 실제 운영 DB 권한은 이번 감사에서 조회하지 않았다.
- 조치:
  - migration owner와 runtime app role 분리, app role에서 DDL·superuser 권한 제거.
  - 테넌트 키를 모든 관련 테이블에 일관되게 두고 가능한 범위에서 RLS/FK/복합 제약 적용.
  - DB TLS 검증, 암호화 백업, PITR, 복구 훈련, 접근 로그를 운영 체크리스트로 검증.

### SEC-020 — MCP가 배포하는 실행 파일의 무결성·배포 완전성 통제 부족

- 심각도: **Medium (공급망/운영)**
- 상태: **확정 설계 개선**
- 근거:
  - `get_worker_command_files`가 고객 저장소에 쓸 커맨드·에이전트 파일 원문을 전달한다(`src/lib/mcp/register-tools.ts:1367-1394`).
  - 파일 목록에는 11개가 있지만(`src/lib/mcp/workerCommandFiles.ts:9-21`), Next output tracing에는 4개만 포함된다(`next.config.ts:25-31`). 서버리스 배포에서 나머지 파일이 누락될 수 있다.

  - tracing 목록을 단일 상수에서 생성하거나 11개 전부 포함하는 빌드 테스트를 둔다.

### SEC-021 — MCP·AI·export·초대 등 비용성 API의 통합 quota/rate limit 부족

- 심각도: **Medium**
- 상태: **확정**
- 근거:
  - DB 기반 rate limiter는 로그인·가입·비밀번호 재설정·refresh 네 곳에 주로 적용된다. MCP 도구, AI 요청, export, 업로드, 초대 발송에는 공통 제한이 없다.
  - `getClientIp()`는 프록시가 헤더를 정리한다는 가정하에 X-Forwarded-For 선두값을 신뢰한다(`src/lib/rateLimit.ts:101-112`). 직접 origin 접근 또는 잘못된 프록시 설정에서는 위조 가능하다.
  - rate-limit DB 오류 시 fail-open한다(`rateLimit.ts:75-88`). 가용성 우선 선택으로 이해 가능하지만 경보가 없다.
- 조치:
  - edge/proxy와 애플리케이션 양쪽에 IP + member + credential + project + operation 단위 제한과 비용 quota를 둔다.
  - 신뢰할 proxy hop을 명시하고 origin 직접 접근을 막는다.
  - fail-open은 유지할 수 있으나 장애 즉시 경보, 고비용 작업은 별도 fail-closed/queue 정책을 사용한다.

## 4. 이미 잘 되어 있는 부분

다음 항목은 실제로 양호하며, 문제처럼 과장할 필요가 없다.

1. **중앙 권한 모델**  
   `permissions.ts`와 `requirePermission.ts`는 역할·직무·플랜을 한 곳에서 평가한다. VIEWER가 직무로 쓰기 권한을 우회하지 못하도록 별도 차단하며, 관련 정책 테스트 8개가 통과했다.
2. **프로젝트 범위 MCP와 WORKER 분리**  
   전역 `ALL` 키를 거부하고 CLIENT/WORKER 용도를 분리한다. 워커는 프로젝트·요청자·ACTIVE 멤버십·삭제 상태를 서버가 강제한다(`src/app/api/worker/_lib/auth.ts`, `worker/tasks/route.ts`).
3. **MCP 내부 호출의 사용자 토큰 전파**  
   `/api/mcp`가 요청자 토큰을 내부 API에 그대로 전달해 전역 서비스 계정으로 권한이 섞이지 않는다(`src/app/api/mcp/route.ts:37-72`). MCP에는 destructive delete 도구도 의도적으로 등록하지 않았다.
4. **지원 세션의 읽기 전용 설계**  
   비멤버 SUPER_ADMIN은 활성 지원 세션이 있어야 하고, `.read` 외 권한은 차단된다. export도 별도 권한이라 지원 세션에서 대량 유출되지 않는다(`requirePermission.ts:160-228`).
5. **비밀번호와 토큰 기본 품질**  
   bcrypt cost 12, 32-byte random RT/MCP key, RT와 MCP 키의 DB hash 저장, 로그인 잠금, RT reuse 탐지, 주요 인증 엔드포인트 rate limit이 구현돼 있다.
6. **프로젝트 삭제 기본 경로**  
   OWNER + 명시적 확인 + 기본 14일 soft-delete + 복구·배치 hard-delete 구조는 안전하다. SEC-003의 탈퇴 우회 경로만 제거하면 된다.
7. **스펙 동기화의 변경 통제**  
   기능 플래그 기본 off, submit/review/apply 권한 분리, 요청자 바인딩, 경로 정규화와 비밀 경로 제외, 증거 hash, target snapshot, row lock, 적용 전 hash conflict 확인, 사람 승인 적용이 구현돼 있다. migration 테스트 3개와 결과 validator가 통과했다.
8. **보안 응답 헤더의 기본선**  
   HSTS(prod), CSP, frame 차단, nosniff, Referrer-Policy, Permissions-Policy가 전역 적용된다. CSP의 `unsafe-inline`은 SEC-005 때문에 강화가 필요하지만 헤더 자체가 없는 상태는 아니다.
9. **런타임 SQL 인젝션 방어**  
   `src/`의 raw SQL은 확인 범위에서 Prisma tagged template/`Prisma.sql`을 사용한다. `$queryRawUnsafe`는 운영 런타임이 아닌 관리·검사 script에만 있었다. 확인된 SQL injection은 없다.
10. **파일 경로의 현재 사용 방식**  
    저장 파일명은 서버 생성 UUID이고 subpath도 서버가 조립하므로, 원본 파일명의 `../`가 곧바로 저장 경로가 되는 취약점은 확인되지 않았다. 다만 공통 fileStorage 자체에는 root containment가 없어 방어적으로 보강하는 것이 좋다.

## 5. 검토했지만 현재 근거로는 과장하면 안 되는 항목

- **CSRF**: 현재 주요 API 인증은 Authorization bearer header이고 세션 쿠키를 자동 전송하지 않으므로 전통적인 CSRF 위험은 낮다. 향후 RT를 쿠키로 옮기면 Origin/CSRF 방어를 같이 도입해야 한다.
- **SVG 업로드 = 즉시 XSS**: 확장자만으로 SVG를 이미지로 분류하는 것은 좋지 않지만, 현재 UI가 인증 fetch 후 blob을 `<img>`로 표시하는 경로에서는 SVG script 실행이 일반적으로 제한된다. 확정 XSS는 HTML/Markdown sink 쪽이다.
- **`unsafe-inline` 자체**: CSP의 약점이지 단독 취약점은 아니다. 이번에는 실제 미정화 HTML sink가 있으므로 영향 증폭 요인으로 평가했다.
- **RLS 부재**: RLS는 필수 기술 선택이 아니며 애플리케이션 검증만으로도 안전할 수 있다. 다만 현재 IDOR가 여러 건이어서 방어 계층으로 권고한다.
- **`/api/health` 공개**: DB 연결 성공 여부만 반환하고 상세 버전·쿼리·비밀을 노출하지 않아 현재 수준은 허용 가능하다. edge에서 호출 빈도만 제한하면 된다.
- **암호화된 외부 AI 키**: 현재 `decryptApiKey()` 사용처가 없어 즉시 제3자 API 탈취로 이어지는 실행 경로는 없다. 운영 활성화 전에 SEC-012를 고쳐야 한다.
- **의존성 CVE**: 온라인 advisory 감사를 완료하지 못했으므로 “취약점 없음”도 “특정 CVE 존재”도 주장하지 않는다.

- [ ] 초대 토큰은 지정 이메일의 단일 계정만 한 번 수락 가능
- [ ] 무료·만료 계정의 유료 AI API/MCP 직접 호출 차단
- [ ] 파일 크기·개수·tenant quota·종류·악성 파일 정책 적용
- [ ] SUPER_ADMIN 로그아웃/세션 강제 종료 즉시 기존 AT 거부

- `npm run test:spec-sync` — stale Prisma client 타입 때문에 compile 단계 실패
- `npm audit --omit=dev` — 격리 환경의 registry 접근 실패 후 외부 전송 승인이 허용되지 않아 미수행
- 실제 운영 클라우드/IAM/WAF/TLS/DB role/백업/로그/키 유효성에 대한 동적 검증 미수행
