# 설계 기반 단위·통합 테스트 MCP 점검

> 후속 수정 완료: 연결 조회·보존, 케이스 선택 필드 보존, 웹 케이스 소유 검증,
> 메타 전용 PATCH/MCP, 통합 시나리오 지침, 미실행 구분·종료 차단을 적용했다.
> 회차에서 사용한 케이스는 변경·삭제를 차단하여 과거 판정 기준을 보존한다.
> DB 구조 및 과거 완료 회차 데이터를 변경하지 않았다. 배포는 하지 않았다.
> 아래 본문은 수정 전 진단 기록이다. 재현용 tmp 스크립트는 회귀 테스트로 교체했다.
> 검증: `npm run test:qa-mcp` 11개, `npm run test:xlsx-test-spec` 8개 통과.
> 타입 검사는 기존 결제 관련 7개 오류가 남아 있다. 실제 DB 동시성·운영 브라우저 검증은 미실시.
> 운영 확인 항목은 `md/QA_MCP_ACCEPTANCE_2026-10-02.md` 참조.

점검일: 2026-10-02

판정: 최초 명세 생성에 필요한 기반은 갖춰져 있다. 다만 웹과 MCP를 함께 쓰거나 설계 변경 후 기존 테스트를 보강하는 과정에는 데이터 보존 문제가 있어, 현재 상태를 부족함 없다고 보기는 어렵다. 전면 재설계보다 아래 오류 수정과 생성 지침 보강이 적절하다.

## 범위와 검증 한계

- 사용자 목적: 단위업무 또는 화면 중심 단위 테스트, 한 개 또는 여러 단위업무의 흐름을 검증하는 통합 테스트를 설계에서 생성하여 MCP로 등록.
- 로컬 작업 트리의 MCP 도구, 설계 조회, QA API, 상세·목록 화면, 단위업무 메뉴, Prisma 관계, 회차 처리, 기본 양식을 확인했다.
- 제공한 운영 URL 3개는 웹 조회 도구로 열리지 않았다. 운영 데이터, 실제 배포 버전, 로그인한 화면 동작을 검증한 것은 아니다.
- 규칙 파일은 `.claude/develop`, `.claude/biz`, `.claude/design`, `.claude/database`에서 확인했다. 로컬 `md/prd`에는 이번 대상 PRD가 없고 UW-00036 문서만 있어, 해당 업무의 PRD 준수 여부는 확정하지 않았다.
- 운영 API 쓰기·DB 접근·마이그레이션을 하지 않았다. 애플리케이션 소스도 수정하지 않았다. 점검용 스크립트와 이 보고서만 추가했다.
- 작업 트리에 있던 별도 변경은 그대로 두었다.

## 이미 지원되는 것

| 필요한 기능 | 현재 구현 |
|---|---|
| 설계 읽기 | `get_design_tree`가 UW 설명과 화면→영역→기능의 설명을 반환. 최대 20 UW씩 조회 가능 |
| 화면/UW 기준 테스트 | `create_test_spec`에서 `unitWorkIds`, `screenIds` 배열 지원. 화면 없는 UW도 대상으로 지정 가능 |
| 여러 UW의 통합 테스트 | INTEGRATION 명세서에 여러 UW 연결 가능. 별도 N:M 연결 테이블 존재 |
| 양식과 공통 점검 | `get_test_template`, `list_check_masters`, `import_check_masters` 지원 |
| 기능 시나리오 | 내용·예상결과·전제조건·데이터·계정·우선순위·AI 생성 여부 저장 가능 |
| 기존 테스트 보강 | 목록/상세 조회 후 `testCaseId`로 수정 가능. MCP 전용 API는 보내지 않은 케이스를 삭제하지 않음 |
| 진행중 회차에 신규 케이스 반영 | 신규 결과행을 같은 트랜잭션에서 추가. 완료 회차에는 신규 결과행을 추가하지 않음 |
| 실제 실행과 분리 | MCP는 명세 작성까지 지원. 실제 수행 없는 PASS/FAIL 기록을 유도하지 않는 정책은 목적에 부합 |

따라서 별도의 서버 AI 생성 API가 없다는 점 자체는 결함이 아니다. MCP를 쓰는 AI가 설계를 읽고 케이스를 작성한 뒤 기존 도구로 등록할 수 있다.

## 실제 오류 및 빠진 기능

### 1. 화면 기준 테스트가 UW에서 누락되고, 이중 연결도 웹 저장으로 소실됨 — 우선 수정

재현 흐름:

1. UW-A에 속한 화면 S를 `screenIds:[S]`로 연결하여 단위 테스트를 생성한다.
2. UW-A의 테스트 메뉴는 `?unitWorkId=UW-A`로 조회한다.
3. 서버 필터는 직접 UW 연결만 검사하므로 S에만 연결된 명세서가 나오지 않는다.
4. 이를 피하려고 MCP에서 UW-A와 S를 둘 다 연결하면 생성은 가능하다.
5. 웹 상세는 화면 연결이 있으면 SCREEN 모드를 선택하고 저장 시 UW 배열을 비운다. 서버가 기존 UW 연결을 삭제하므로 메뉴에서 다시 빠진다.

영향: 실제 작성한 테스트를 UW에서 찾지 못하고, AI가 같은 대상에 중복 명세를 만들 수 있다. 단위업무와 화면을 오가는 사용자 흐름의 직접적인 결함이다.

근거:

- `src/app/api/projects/[id]/test-specs/route.ts:61` — `uwLinks.some`만 필터.
- `src/components/test-specs/UwTestSpecMenu.tsx:61` — UW 필터로 조회.
- `src/app/(main)/projects/[id]/test-specs/[specId]/page.tsx:205` — 화면이 있으면 SCREEN 선택.
- 같은 파일 `:225` — 선택하지 않은 종류의 연결을 빈 배열로 전송.
- `src/app/api/projects/[id]/test-specs/[specId]/route.ts:251` — 연결 전체 재구성.

최소 개선: UW 조회에 소속 화면 연결도 포함하고, 웹에서 사용자가 제거하지 않은 연결을 보존한다. 화면 테스트와 UW 테스트를 별도 중복 생성하는 방식으로 우회하지 않는다.

### 2. MCP 케이스 수정 시 선택 필드가 초기화됨 — 우선 수정

기존 케이스의 `testCaseId`, `ctgryCode`, `scenarioCn`, `expectedCn`만 전송해 문장을 수정하면, 생략한 전제조건·데이터·계정·그룹·비고가 NULL로 바뀌고 우선순위는 MEDIUM, 해당 여부는 Y, AI 표시는 N으로 돌아간다.

선택 필드로 노출된 MCP 인터페이스와 일반적인 부분 수정 기대가 맞지 않는다. 특히 기존 해당없음 케이스가 적용 대상으로 바뀌거나 사람이 준비한 테스트 계정이 사라진다.

근거: `src/app/api/projects/[id]/test-specs/[specId]/cases/route.ts:169`의 `caseData`를 생성·수정에 공통 적용, `:176`부터 생략값에 기본값 부여, `:186`의 UPDATE.

최소 개선: 신규일 때만 기본값을 적용하고 기존 수정에서는 전송된 필드만 변경한다. 명시적인 값 비우기 방식도 MCP 스키마와 함께 정의한다.

### 3. 완료된 회차가 당시 명세를 보존하지 못함 — 우선 수정

완료 회차의 결과행은 같은 `test_case_id`를 계속 참조하고, 조회 시 현재 케이스 문장을 조인한다. 따라서 MCP로 예상결과를 수정하면 과거 PASS도 새 예상결과 기준으로 표시된다. 케이스를 웹에서 삭제하면 CASCADE 관계로 과거 결과까지 삭제될 수 있다.

완료 회차에 새 결과행을 추가하지 않는 보호는 잘 되어 있지만, 그것만으로 당시 기록 전체가 고정되지는 않는다. 정책의 “완료된 회차에는 아무 영향이 없다”는 설명은 케이스 수정까지 포함하면 성립하지 않는다.

근거:

- `src/app/api/projects/[id]/test-specs/[specId]/rounds/[roundId]/route.ts:39`, `:69` — 현재 testCase 조인·표시.
- `prisma/schema.prisma:2147` — 결과에 당시 케이스 본문 스냅샷 없음.
- `prisma/schema.prisma:2161` — 케이스 삭제 시 결과 CASCADE.
- `src/lib/mcp/test-policy.ts:116` 부근 — 완료 회차 영향 없음 안내.

최소 개선: 당장은 판정 이력이 있는 케이스의 본문 변경·삭제를 제한하고 새 케이스로 대체하게 할 수 있다. 장기적으로 회차별 케이스 버전 또는 실행 시점 스냅샷이 적절하다. 결과표뿐 아니라 결과서 내보내기도 같은 기준을 써야 한다.

### 4. 미실행과 해당없음이 NA로 섞여 미검증 명세도 합격 가능 — 실행 관리 보완

회차 생성과 MCP 신규 케이스 동기화는 결과 기본값을 NA로 만든다. UI에서는 NA를 해당없음으로 표시한다. 회차 종료 API는 FAIL/BLOCKED가 없으면 PASSED로 전환하므로, 모든 결과가 기본 NA여도 합격한다.

영향: AI가 새 테스트를 잘 만들어도 사람이 판정을 빠뜨린 채 종료하면 전체 합격으로 보일 수 있다. 생성 자동화 자체를 막지는 않지만 결과 신뢰도 문제다.

근거:

- `src/app/api/projects/[id]/test-specs/[specId]/rounds/route.ts:128` — 초기 NA.
- `src/lib/qa/roundResultSync.ts` — 신규 결과도 NA.
- `src/components/test-specs/TestRunPanel.tsx:73` — NA=해당없음.
- `src/app/api/projects/[id]/test-specs/[specId]/rounds/[roundId]/route.ts:219` — FAIL/BLOCKED 유무만으로 판정.

최소 개선: 미실행 상태와 해당없음을 구분하고 적용 대상 중 미실행이 남으면 완료/합격을 제한한다.

### 5. 기존 명세서의 개요·대상 연결을 수정하는 MCP 도구가 없음 — 반복 사용에 필요

QA MCP는 조회, 생성, 공통 점검 가져오기, 케이스 추가·수정만 제공한다. 기존 통합 테스트의 범위를 UW-A/B에서 UW-A/B/C로 확장하거나 개요를 최신 설계에 맞춰 고칠 방법이 없다. 케이스는 바뀌는데 헤더의 범위는 오래된 채 남을 수 있다.

근거: `src/lib/mcp/register-tools.ts:1862` 이후 QA 등록 도구 전체. 웹 PUT은 있지만 케이스 전체 저장·누락 삭제가 결합되어 MCP에 그대로 노출하기에는 부적합하다.

최소 개선: 케이스를 건드리지 않는 명세 메타/대상 수정 API와 `update_test_spec` 도구를 추가한다. 사용자 요청이 범위 확장을 이미 승인했다면 불필요하게 매 항목 재승인을 요구할 필요는 없다.

## 자동 생성 품질을 위한 보완 — 저장 불가능한 결함과 구별

### 통합 테스트 생성 지침

현재 데이터 구조로도 여러 단계의 통합 시나리오를 텍스트로 저장할 수 있다. 단계 테이블이나 새로운 실행 엔진을 반드시 만들 필요는 없다.

다만 `src/lib/mcp/test-policy.ts`와 기본 양식 `scripts/create-test-spec-design-template.sql`은 기능당 정상 1건+예외, 화면 내 그룹, 화면에서 관측 가능한 결과를 중심으로 한다. INTEGRATION 전용 생성 기준은 없다. 여러 UW를 연결하는 것만으로 UW 사이 흐름을 검증하는 케이스가 자동 보장되지는 않는다.

권장 기준:

- UNIT: 한 UW 또는 화면 내부 행위와 규칙을 검증. 화면 없는 업무는 API 응답·처리 상태 등 적절한 관측 지점 사용.
- INTEGRATION: 한 UW 안의 여러 처리 단계 또는 여러 UW 사이의 업무 흐름을 검증. 반드시 UW가 두 개 이상일 필요는 없음.
- 설계에 있는 시작 조건 → 실행 순서 → 다음 단계로 전달되는 데이터/상태 → 최종 결과를 작성.
- 설계에 정의된 연계 실패·중복·권한·취소/복구 흐름이 있으면 포함. 없는 동작을 상상해서 만들지 않음.
- 예: 주문 등록 → 승인 → 후속 처리. 각각의 화면 정상 동작을 나열하는 대신 같은 주문이 다음 단계에 전달되고 올바른 상태로 종료되는지 확인.
- 현재 `scenarioCn`, `expectedCn`, `preconditionCn`, `testDataCn`, `grpNm`에 번호 있는 단계와 판정 기준을 담는 것부터 시작 가능.

### 재생성·누락 확인

기존 상세를 읽고 ID를 유지해 수정하면 현재 도구로도 운영할 수 있다. 다만 ID 없는 동일 신규 케이스를 재전송하면 그대로 중복 INSERT된다. 또한 케이스에 기능/요구사항 원본 ID나 설계 버전이 없어, 어떤 설계가 테스트로 다뤄졌는지 프로그램이 확정하기 어렵다.

이것을 최초 도입의 절대 차단 요건으로 보지는 않는다. 우선 생성 결과에 대상 UW/PID/FUNC 표시 ID와 추가·수정·유지 내역을 보고하도록 하고, 반복 자동화 범위가 커질 때 출처 연결과 요청 재시도 중복 방지를 추가하는 것이 적절하다. 문장이 같다는 이유만으로 무조건 같은 케이스로 합치면 데이터/조건이 다른 테스트를 잃을 수 있으므로 주의한다.

## 별도 보안 확인 사항

웹 일괄 PUT은 명세서 프로젝트와 연결 대상 소속은 검사하지만, 입력된 `testCaseId`가 해당 명세서 소유인지 확인하지 않고 ID 단독으로 UPDATE한다 (`src/app/api/projects/[id]/test-specs/[specId]/route.ts:301`). 다른 명세서의 ID를 넣으면 그 케이스를 수정할 수 있는 구조다. MCP 전용 `/cases`에는 소유 검증이 이미 있으므로 같은 검증을 웹 PUT에도 적용해야 한다. 이 항목은 소스 확인이며 운영 요청으로 재현하지 않았다.

## 검증 결과

- `node tmp/qa-mcp-review.cjs`: 실제 route.ts를 TypeScript 변환 후 DB·권한 모듈을 메모리 대역으로 교체하여 실행. 운영 접근 없음.
  - 선택 필드 생략 시 기존 값 초기화 재현.
  - 완료 PASS 회차에 수정된 예상결과가 표시됨을 재현.
  - 동일 신규 케이스 재전송 시 중복 생성 확인.
  - 모든 결과 NA인 회차가 PASSED로 종료됨을 재현.
  - UW 목록 조회의 직접 연결 필터 확인.
  - 웹 이중 연결 손실 경로는 소스 조건 검사로 확인. 브라우저 E2E는 아님.
- `npm run test:xlsx-test-spec`: 기존 엑셀 생성 검증 8항목 통과. 파일 생성/회차 시트 구조 확인이며 위 데이터 보존 문제의 부재를 증명하는 테스트는 아님.
- `npm run typecheck`: 실패. 결제 코드의 Prisma 필드 `pndng_lock_key`, `pndng_meta_json` 타입 불일치 및 `@tosspayments/tosspayments-sdk` 모듈 누락, 총 7개 오류. 출력에 이번 QA 대상 파일의 오류는 없었다. 전체 빌드 정상 판정은 하지 않음.

## 권장 진행 순서

1. 연결 보존·조회와 케이스 부분 수정 보존을 먼저 수정한다. 웹 PUT 소유 검증도 함께 수정한다.
2. 명세 메타 수정 MCP를 추가하고 UNIT/INTEGRATION 생성 지침을 분리한다.
3. 완료 회차의 기준 보존과 미실행 상태를 보완한다.
4. 사용자 프로젝트의 실제 설계를 읽어 대표 UNIT 1개와 INTEGRATION 1개를 작성·검토한 뒤 범위를 넓힌다.

색상·간격·컴포넌트 분리·명칭 취향 같은 사항은 이번 목적의 핵심 결함으로 세지 않았다. 결과 입력 MCP 미지원, 케이스 삭제 MCP 미지원, 20 UW 배치 조회 역시 현재 정책과 용도에 맞는 제약으로 보았다.
