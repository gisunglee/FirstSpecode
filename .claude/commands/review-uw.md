# /review-uw — SPECODE UW 구현 품질 검토

SPECODE 서버에 저장된 **현재 설계**와 **표준 가이드**(로컬 파일 아님)를 기준으로 특정
UW(단위업무) 구현을 병렬 검토하고 종합 리포트를 출력한다. 둘 다 실행할 때마다 서버에서
새로 조회한다 — 과거에 내려받은 스냅샷이나 로컬 문서를 기준으로 삼지 않는다.

이 명령과 서브에이전트는 **어떤 특정 고객 프로젝트에도 종속되지 않는다** — 코드 품질·UI
디자인 검토는 "이 프로젝트가 Next.js를 쓴다" 같은 걸 미리 가정하지 않는다. 그 두 관점은
해당 프로젝트의 SPECODE **표준 가이드**(공통 설계 > 표준 가이드)에 등록된 문서가 있을
때만 동작하고, 없으면 그 관점만 조용히 건너뛴다 — 로컬 파일 경로를 사용자에게 물어보지
않는다.

## 사용법

```
/review-uw <UW번호>
```

예시:
```
/review-uw UW-00014
/review-uw UW-00035
/review-uw 14          ← 숫자만 전달해도 UW-00014 로 정규화
```

## 실행 지시사항

### 실행 전 안내 (필수)

인자 정규화가 끝나 `$UW`가 확정되면, 무거운 작업(프로젝트 확인/서버 조회/서브에이전트 호출)을
시작하기 전에 **먼저 사용자에게 짧게 알린다**:

"{UW}를 SPECODE 서버의 현재 설계와 표준 가이드 기준으로 검토합니다. PRD 준수는 항상
검토하고, 코드 품질·UI 디자인은 이 프로젝트에 등록된 표준 가이드가 있을 때만 검토합니다
(없으면 그 관점만 건너뜁니다). 종합 리포트로 PASS·WARN·FAIL을 보여드리며, 서버에는
아무것도 저장되지 않고 자동으로 코드를 고치지도 않습니다. 잠시 걸릴 수 있습니다."

### 0단계: 인자 검증 및 정규화

`$ARGUMENTS` 를 공백으로 토큰 분리.

- **토큰 0개**: 사용법 안내 후 종료.
- **토큰 2개 이상**: 사용법 안내 후 종료.
- **토큰 1개**:
  - `UW-XXXXX` 형식 → 그대로 사용
  - 숫자만 (예: `14`, `35`) → `UW-00014`, `UW-00035` 로 정규화 (5자리 zero-pad)
  - 그 외 형식 → 거부

정규화된 값을 `$UW` 변수로 이후 단계에서 사용.

`mcp__specode__list_projects`로 프로젝트를 확인한다. 하나면 그 ID를 `$PROJECT_ID`로 쓰고,
여러 개면 `AskUserQuestion`으로 선택받는다.

### 1단계: 서버에서 설계 조회

`mcp__specode__list_unit_works($PROJECT_ID)`에서 `displayId`가 `$UW`와 일치하는 항목을
찾는다.

- 없으면 "SPECODE에 해당 UW가 없습니다: {UW}" 출력 후 종료.
- 있으면 그 `unitWorkId`로 `mcp__specode__get_design_tree($PROJECT_ID, [unitWorkId])`를
  호출해서 화면>영역>기능 전체 계층과 각 레벨의 설명(description)을 확보한다. 이 결과가
  `$DESIGN_TREE`다.
- `$DESIGN_TREE`의 화면 목록이 비어 있으면(화면 없는 순수 백엔드 UW 등), `prd-compliance-reviewer`
  호출 자체는 그대로 하되(3단계에서 항상 호출하는 대상이다) 프롬프트에 "이 UW는 설계상
  화면이 없다 — 화면/영역/기능 대조 대신 참조 테이블·백엔드 계약 정도만 확인하거나, 검토할
  대상이 없으면 PASS로 판정하고 그 사실을 summary_ko에 남겨라"라고 명시해서 전달한다.

이 단계는 실행마다 새로 조회한다 — 이전 실행 결과를 재사용하지 않는다.

### 2단계: 코드 품질·UI 디자인 기준 문서 조회 (SPECODE 표준 가이드)

`code-quality-reviewer`와 `ui-design-reviewer`는 로컬 파일이 아니라 SPECODE 서버의
**표준 가이드**(웹의 공통 설계 > 표준 가이드)를 기준 문서로 쓴다. 사용자에게 경로를
물어보지 않는다 — 프로젝트에 등록돼 있으면 자동으로 쓰고, 없으면 그 관점만 조용히
건너뛴다.

1. `mcp__specode__search_standard_guides($PROJECT_ID)`를 카테고리 필터 없이 호출한다
   (도구 기본값이 사용중인 가이드만 반환한다 — 미사용으로 꺼둔 가이드는 자동 제외). 이
   시점엔 제목·카테고리만 있고 본문은 없다 — 아직 `get_standard_guide`를 부르지 않는다.
2. 결과를 카테고리로 3그룹으로 나눈다:
   - `category === "UI"` → UI 디자인 후보 (전부 포함, 필터링 없음)
   - `category`가 `COMMON`/`SECURITY`/`ERROR` → 코드 품질 **필수** 후보 (전부 포함,
     필터링 없음 — 이 세 카테고리는 어떤 UW를 검토하든 항상 관련 있다고 본다: 공통 규칙과
     보안·에러 처리는 특정 기능에 국한되지 않고 매 기능마다 새로 지켜져야 하는 것들이다)
   - `category`가 `DATA`/`AUTH`/`API`/`FILE`/`BATCH`/`REPORT` → 코드 품질 **선택** 후보.
     각 가이드의 **제목**을 `$DESIGN_TREE`(이 UW의 화면·기능·설명)와 대조해서, 이 UW와
     관련 있어 보이는 것만 남긴다. 판단이 애매하면 **포함한다**(관련 있는 걸 빼는 것보다
     안전) — 명백히 무관해 보일 때만 제외한다(예: 이 UW에 배치 관련 기능이 전혀 없는데
     "배치 잡 실패 재시도 정책"이라는 제목의 가이드).
3. 남은 후보(UI 전부 + 코드 품질 필수 전부 + 코드 품질 선택 중 관련 있다고 판단된 것)
   각각에 대해 `mcp__specode__get_standard_guide($PROJECT_ID, guideId)`를 호출해서 본문
   (content)까지 확보한다. UI 후보들의 "제목 + 본문"을 이어붙인 것이 `$UI_DESIGN_GUIDES`,
   코드 품질 후보(필수+선택)들을 이어붙인 것이 `$CODE_QUALITY_GUIDES`다.
4. 어느 한쪽 후보가 없으면(그 카테고리에 등록된 표준 가이드가 아직 없거나, 선택 후보가
   전부 무관하다고 판단됨) 그 관점만 건너뛴다. 둘 다 없으면 두 관점 모두 건너뛰고, 최종
   리포트에 "SPECODE 웹의 공통 설계 > 표준 가이드에서 등록하면 검토됩니다"라고 안내한다.
5. 코드 품질 관점이 실행됐으면, 최종 리포트의 코드 품질 섹션에 "필수 N개 + 관련 있다고
   판단한 선택 M개(전체 후보 중)"를 한 줄로 짧게 남긴다 — 어떤 기준으로 골랐는지 사용자가
   바로 알 수 있게.

이 단계도 실행마다 새로 조회한다 — 과거에 어떤 가이드가 있었는지 기억하거나 캐시하지
않는다.

### 3단계: 서브에이전트 병렬 호출

**반드시 한 번의 응답에서 Agent 툴을 호출 (병렬 실행)**. 호출 대상은 조건부다:

- `prd-compliance-reviewer`: 항상 호출.
- `code-quality-reviewer`: `$CODE_QUALITY_GUIDES`가 비어 있지 않을 때만 호출. 비어 있으면
  **호출 자체를 하지 않는다** — 대신 6단계 출력에서 "⏭️ 건너뜀 — 표준 가이드 미등록"으로 표기.
- `ui-design-reviewer`: `$UI_DESIGN_GUIDES`가 비어 있지 않을 때만 호출, 비어 있으면 마찬가지로
  호출하지 않고 건너뛴다.

`$DESIGN_TREE`는 오케스트레이터(이 명령)가 **한 번만** 조회하고, 그 결과를 각 에이전트
프롬프트에 텍스트로 그대로 붙여서 전달한다 — 각 에이전트가 서버를 다시 조회하지 않는다
(중복 조회 방지, 에이전트는 MCP 권한 없이 순수 읽기 전용 유지). 표준 가이드 본문도 마찬가지로
오케스트레이터가 이미 조회한 텍스트를 그대로 붙여서 전달한다 — 에이전트가 따로 조회하지 않는다.

**prd-compliance-reviewer 프롬프트**:

````
대상: {UW}

아래는 SPECODE 서버에서 방금 조회한 이 UW의 현재 설계 트리(화면>영역>기능 계층, 각
description 포함)다. 로컬 PRD 파일은 없으니 이 설계 트리를 기준으로 검토한다.

{화면 목록이 비어 있으면 여기에 1단계에서 정한 안내 문장 삽입: "이 UW는 설계상 화면이
없다 — 화면/영역/기능 대조 대신 참조 테이블·백엔드 계약 정도만 확인하거나, 검토할
대상이 없으면 PASS로 판정하고 그 사실을 summary_ko에 남겨라."}

```json
{DESIGN_TREE_JSON}
```

검토해서 JSON 리포트 + 한국어 요약으로 리턴해줘.
반드시 .claude/agents/_shared/report-format.md 포맷 준수.
````

**code-quality-reviewer 프롬프트** (호출하는 경우) — prd-compliance와 마찬가지로
`$DESIGN_TREE`를 함께 넣어서 URL/API 추출에 쓸 수 있게 하고, 기준 문서는 경로가 아니라
**본문 텍스트를 그대로** 넣는다:

````
대상: {UW}

아래는 이 프로젝트의 SPECODE 표준 가이드(코드 품질 관련 카테고리) 본문이다 — 이게 이번
검토의 기준 문서다. 로컬 파일을 따로 찾지 마라:

---
{CODE_QUALITY_GUIDES}
---

아래는 이 UW의 현재 설계 트리다(화면 URL·기능 API 경로 참고용, 선택적으로 활용):

```json
{DESIGN_TREE_JSON}
```

위 기준 문서를 근거로 검토해서 JSON 리포트 + 한국어 요약으로 리턴해줘. 반드시
.claude/agents/_shared/report-format.md 포맷 준수.
````

**ui-design-reviewer 프롬프트** (호출하는 경우): 위와 동일한 형태(설계 트리 + 기준 문서
본문 텍스트 포함)로 `$UI_DESIGN_GUIDES`를 "기준 문서" 자리에 넣어서 전달한다.

**주의**:
- 모든 에이전트는 **isolation 불필요** (읽기 전용 작업). 워크트리 옵션 주지 말 것.
- 백그라운드(run_in_background) 금지. 결과를 다음 단계에서 바로 써야 함.
- 호출한 에이전트의 JSON 블록이 모두 돌아올 때까지 대기.

### 4단계: 리포트 수집 및 파싱

각 에이전트 응답에서 ```json 블록 추출 → 파싱.

- 파싱 실패 시: 해당 에이전트 이슈는 "리포트 파싱 실패"로 기록, 종합 판정은 나머지로 진행.
- `verdict: "SKIPPED"`가 온 리포트(에이전트가 스스로 기준 문서 없다고 판단한 경우)는
  2단계에서 걸러졌어야 정상이지만, 혹시 오면 건너뜀 목록에 추가하고 종합 판정에서 제외.

### 5단계: 종합 판정

**참여한(호출되어 실제로 결과가 온) 리뷰어만으로** 집계한다. prd-compliance는 항상
참여하므로 최소 1개는 있다.

**verdict 집계 규칙** (가장 나쁜 것 따라감, 참여한 리뷰어 기준):
- 하나라도 FAIL → **종합 FAIL**
- 하나라도 WARN → **종합 WARN**
- 참여한 리뷰어 전부 PASS → **종합 PASS**

**score 종합**: 참여한 리뷰어 score의 **최솟값**.

**counts 합산**: 참여한 리뷰어들의 critical/major/minor 각각 합산.

건너뛴 관점(표준 가이드 미등록)은 판정·점수·카운트 계산에서 **완전히 제외**한다 — FAIL이나
0점으로 취급하지 않는다.

### 6단계: 종합 리포트 출력

사용자에게 아래 구조로 출력한다. **건너뛴 관점은 판정/점수 없이 "건너뜀" 표시만** 하고,
참여한 관점만 판정·점수·이슈를 표시한다.

### 7단계: 자동 수정 여부

**디폴트: 자동 수정 금지**. 리포트만 출력하고 종료.

사용자가 이어서 "critical 부터 고쳐줘" 같은 지시 주면 그때 수정 진행.

---

## 주의사항 (체크리스트)

- [ ] UW 번호 없으면 사용법만 출력하고 종료
- [ ] 프로젝트 확인(하나면 자동, 여러 개면 질문) 후 진행
- [ ] SPECODE 서버에서 설계 트리 조회(`get_design_tree`) 후 에이전트 호출 — 로컬 PRD 파일 사용 금지
- [ ] 설계 트리는 오케스트레이터가 1번만 조회해서 프롬프트로 전달 (중복 조회 금지)
- [ ] 코드 품질/UI 디자인 기준 문서는 `search_standard_guides`/`get_standard_guide`로 매번
      서버에서 조회 — 로컬 파일 경로나 사용자 질문으로 대체하지 않는다
- [ ] 기준 문서(표준 가이드)가 없는 관점의 서브에이전트는 **호출 자체를 하지 않는다**
      (SKIPPED로 때우지 않음)
- [ ] 어떤 특정 파일 경로(A-NEXTJS-기술규칙.md 등)나 로컬 설정 파일을 코드에서 직접
      가정하지 않는다
- [ ] Agent 툴을 **같은 응답에 병렬 호출** (순차 금지)
- [ ] 참여한 리뷰어 리포트 모두 수신 후 종합 판정 (건너뛴 관점은 집계에서 제외)
- [ ] JSON 파싱 실패 시 해당 에이전트만 skip, 전체 중단 금지
- [ ] 디폴트는 **리포트 출력만**. 자동 수정 금지
- [ ] 출력은 한국어로

## 설계 메모

- 루프 깊이: **1회** (자동 반복 수정 안 함. 리스크 관리)
- 플랫폼 원칙: 이 명령과 서브에이전트는 여러 고객 프로젝트에 동일하게 배포된다. 특정
  프로젝트에만 있는 로컬 파일을 하드코딩해서 참조하지 않는다 — 대신 SPECODE 서버의
  프로젝트별 데이터(설계 트리, 표준 가이드)를 실행마다 조회한다. 그래서 로컬 설정
  파일이나 사용자 확인 질문이 필요 없다 — 팀원 누가 어느 컴퓨터에서 돌려도 항상 같은
  최신 기준을 본다.
- 표준 가이드가 비어 있는 프로젝트(막 시작한 프로젝트 등)에서는 code-quality/ui-design이
  조용히 건너뛰어진다 — 우회 절차나 로컬 대체 입력은 두지 않는다. 검토받고 싶으면 SPECODE
  웹에서 가이드를 등록하면 된다.
- UI 리뷰 범위: **토큰 검사 + 패턴 일관성 비교**. 스크린샷 비교는 미지원
- 에이전트는 읽기만. Edit/Write 권한 없음 (tools 필드에서 제한됨), MCP 권한도 없음 —
  설계 데이터와 표준 가이드 본문은 오케스트레이터가 확보해서 프롬프트로 주입
- `/sync-specode`와의 관계: 이 명령은 서버에 결과를 남기지 않는 **즉석 셀프 체크**용이고,
  `/sync-specode`는 서버에 실행 이력을 남기고 웹에서 사람이 승인하는 **공식 절차**용이다.
  둘 다 "설계가 주(主)"라는 같은 판단 기준(설계에 없는 것을 억지로 지적하지 않음, 설계에
  있는데 빠진 것 위주로 지적)을 따르므로 같은 UW에 대해 서로 모순되는 결론을 내지 않는다.
- 필요 시 `/review-uw` 리포트 받은 뒤 메인에게 "이슈 수정해줘" 하면 메인이 수정
