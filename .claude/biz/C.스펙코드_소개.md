# 스펙코드(SPECODE) 소개

> AI와 구현하기 전에, AI와 설계하세요.

---

## 1. 한 줄 정의

**AI와 대화하며 정한 분석·설계 결정을 정해진 구조에 쌓아 두고, 그것을 AI가 개발에 바로 쓸 수 있는 MD(PRD)로 뽑아 주는 도구.**

내부에서는 짧게 "MD 파일 메이커"라고 부른다. 다만 핵심은 MD라는 결과물보다
**그 MD를 만들기까지의 구조와 축적**에 있다.

---

## 2. 왜 만들었나

바이브 코딩으로 화면과 기능은 빨리 나온다. 문제는 그다음이다.

- **대화는 끝나면 사라진다.** AI와 나눈 대화 안에는 업무 규칙, 화면 흐름, 테이블 구조에 대한
  결정이 가득하다. 그런데 대화가 끝나면 그 결정도 같이 흩어진다. 다음 날 같은 설명을 또 해야 한다.
- **AI는 지금 소스만 보고 추측한다.** 유지보수 시점에 AI에게 주어지는 건 현재 코드뿐이다.
  왜 이렇게 만들었는지, 무엇을 일부러 뺐는지는 코드에 없다.
- **팀에 공유되지 않는다.** 개발자가 AI에게 전달한 맥락은 그 사람의 대화창에만 남는다.
  다른 팀원은 결과물만 보고 의도를 짐작해야 한다.
- **중요한 업무일수록 맡기기 어렵다.** 업무 규칙이 복잡한 중·대규모 시스템은 설계서 한 장 없이
  AI만 믿고 구현을 맡기기 어렵다. 변경 영향을 설명할 수 없는 시스템은 운영 단계에서 손대기가 겁난다.

Claude 팀 요금제 같은 공유 수단도 있지만, "대화"를 공유하는 것과 "확정된 설계"를 공유하는 것은 다르다.

---

## 3. 핵심 컨셉 — 대화하고, 그 결과를 구조에 남긴다

```
 AI와 대화 (Claude Code 등)          스펙코드                      개발
 ─────────────────────────   →   ─────────────────────   →   ─────────────
 질문하고, 답하고, 맞다/틀리다        정해진 구조에 저장             MD(PRD)를 AI에 주고
 따져 가며 결정                      (계층 + 항목별 양식)            구현
```

누구나 AI와 대화해서 설계를 뽑아낼 수는 있다. 보통은 거기서 끝난다.
스펙코드가 다른 점은 두 가지다.

1. **구조가 이미 잡혀 있다.** 과업부터 기능까지 계층이 게시판처럼 연결돼 있다.
   각 계층에 무엇을 채워야 하는지(목적, API 주소, 사용하는 컬럼, 예외 규칙 등)도 표준 양식으로 정해져 있다.
   이 구조를 매 프로젝트마다 직접 만드는 수고가 사라진다.
2. **구조가 질문지가 된다.** 채워야 할 칸이 정해져 있으니 AI와 대화할 때 무엇을 물어봐야 하는지가 분명하다.
   빈칸이 보이면 빠진 것이 보인다. 그냥 대화할 때는 아무도 묻지 않았던 부분이 드러난다.

결과적으로 **대화는 흘러가도 결정은 남는다.** 남은 결정은 팀원, 다음 담당자, 그리고 유지보수하는 AI가 같이 본다.

---

## 4. 구조 — 무엇을 어떤 단위로 남기나

### 분석

| 계층 | 담는 것 |
|---|---|
| **과업** | 제안요청서(RFP)·과업지시서의 요구 내용. 프로젝트의 출발점 |
| **요구사항** | 과업을 만들기 좋은 의미 단위로 나눈 것. 인터뷰에서 확인한 업무 규칙과 배경 |
| **사용자스토리** | 페르소나, 시나리오, 인수 조건. AI가 의도와 완료 기준을 이해하는 근거 |

### 설계

| 계층 | 담는 것 | 예 (게시판) |
|---|---|---|
| **단위업무** | 의미 있는 업무 묶음 | 멀티 게시판 |
| **화면** | 사용자가 마주하는 실제 화면 | 목록 · 상세 · 등록 |
| **영역** | 화면을 역할별로 나눈 구역. 단순한 화면은 영역 1개로 충분 | 검색+목록 영역 |
| **기능** | 사용자 동작과 시스템 처리. 구현과 검토의 기준 | 키워드 검색, 페이징, 저장 |
| **테이블** | 기능을 뒷받침하는 데이터 구조. 기능과 컬럼 단위로 연결 | tb_board, tb_post |

영역은 잘게 쪼갤수록 좋은 설계가 되는 게 아니다. 관리 비용만 늘어난다.
기본은 화면당 1~3개이고, 권한·저장 단위·탭·담당자가 다를 때만 나눈다.

## 5. 어떻게 채우나 — 세 가지 방법

| 방법 | 설명 |
|---|---|
| **직접 입력** | 스펙코드 화면에서 계층을 따라 입력 |
| **Claude 프로젝트 + JSON** | 스펙코드가 제공하는 전용 프롬프트(표준 양식 포함)를 Claude 프로젝트에 넣고, AI와 문답하며 설계한 결과를 JSON으로 받아 일괄 등록 |
| **MCP 연동** | Claude Code 같은 AI 도구에서 대화하며 바로 조회·등록·수정. 도구 약 67개 제공 (기획·설계 계층, 테이블·컬럼 매핑, 공통코드, 표준 가이드, 테스트 명세 등) |

어느 방법이든 **표준 양식**을 기준으로 채운다. 표준 양식은 계층별로 공통 양식이 있고,
프로젝트마다 따로 바꿀 수도 있다. AI는 등록하기 전에 양식을 먼저 확인한다.
모자란 정보는 추측으로 채우지 않고 사람에게 묻는다.

실제로 가장 효과적인 흐름은 **MCP**다. 분석·설계자가 Claude Code에 충분한 정보를 주고,
무엇이 맞고 틀린지 따져 가며 결론을 내린다. 그러면 그 결론이 곧바로 구조에 저장된다.

## 6. 무엇이 나오나

### PRD(MD) — 핵심 결과물

- 단위업무·화면·영역·기능 중 원하는 단위로 한 번에 MD를 만든다.
  여러 단위업무를 묶거나 프로젝트 전체를 하나로 만들 수도 있다.
- 입력된 설계 내용을 **가공하지 않고** 계층 순서대로 엮는다. AI가 새로 지어내지 않는다.
  그래서 **MD의 품질은 입력한 설계의 품질과 같다.** 대화를 충실히 하고 제대로 남기는 것이 곧 품질이다.

### 제출 산출물 (공공 SI)

같은 설계 정보에서 뽑기 때문에 문서마다 내용을 다시 옮겨 적지 않아도 되고, 문서 사이의 기준도 어긋나지 않는다.

| 산출물 | 형식 | 상태 |
|---|---|---|
| 요구사항 정의서 | docx, xlsx | 제공 |
| 과업대비표 | docx, xlsx | 제공 |
| 요구사항 명세서(요건정의서) | docx (요구사항별) | 제공 |
| 프로그램 사양서 | docx (단위업무별) | 제공 |
| 테이블 목록 | xlsx | 제공 |
| 테스트 명세 | xlsx | 제공 |
| 요구사항 추적표 | — | 미제공 (예정) |
| 속성 정의서 / 컬럼 정의서 | — | 미제공 (예정) |

## 7. 지금 제공하는 부가 기능

핵심(구조화 저장 + MD)을 받쳐 주는 기능들이다.

- **기능·영역 AI 설계/점검** — 자유롭게 적은 기능 설명을 표준 양식으로 정리하고, 누락과 오류를 짚어 준다.
  같은 영역 안의 다른 기능과 비교해 명세를 검토하기도 한다.
- **기획실** — 요구사항과 스토리를 바탕으로 AI가 정보구조도, 화면 흐름, 업무 프로세스, ERD,
  화면 초안(HTML) 같은 초안을 만든다. 확정 문서가 아니라 팀이 검토를 시작하는 출발점이다.
- **테이블·컬럼 관리** — DDL 가져오기, 기능과 컬럼 연결, 특정 컬럼·테이블을 어느 기능·화면이 쓰는지 조회.
- **스펙 동기화** — 구현된 소스와 단위업무 설계를 비교해 어긋난 항목만 올린다. 반영 여부는 항목별로 사람이 결정한다.
- **그 밖에** — 테스트 명세, 표준 가이드, 기존 시스템(AS-IS) 분석 정보 등록.

## 8. 누구를 위한 도구인가

**맞는 팀**
- 요구사항이 복잡하고 제출 산출물이 많은 **공공 SI 사업팀**
- 구축 이후 운영·유지보수까지 설계 기준이 이어져야 하는 프로젝트
- 설계 없는 바이브 코딩의 품질이 걱정돼 AI 도입을 망설이던 **기존 개발팀**

**맞지 않는 경우**
- 개발을 전혀 모르는 사용자. 스펙코드는 노코드 도구가 아니다.
  설계를 아는 사람의 판단을 더 잘 남기고 활용하게 해 주는 도구다.
- 작은 개인 프로젝트나 MVP. 구조를 채우는 비용이 얻는 가치보다 클 수 있다.

---

## 9. 솔직하게 — 한계와 전제

- **입력 비용이 있다.** 계층이 깊고, 처음 채우는 데 품이 든다. AI(JSON·MCP)가 이 부담을 크게 줄여 주지만 0이 되지는 않는다.
- **알아서 설계해 주는 도구가 아니다.** 설계의 선택(A냐 B냐)은 여전히 사람이 판단하고 확정한다.
  스펙코드는 그 판단을 빠짐없이 묻고 남기게 도와줄 뿐이다.
- **유지하는 습관이 필요하다.** 코드만 고치고 설계를 안 고치면 금방 어긋난다.
  스펙 동기화가 이를 잡아 주지만, 결국은 팀의 규율 문제다.
- **AI와 함께 쓸 때 가치가 크다.** AI를 쓰지 않는 팀에게는 무거운 문서 도구로 느껴질 수 있다.

## 10. 앞으로의 과제

지금은 **"잘 구조화된 설계 → AI가 개발을 잘할 수 있는 MD"**가 스펙코드의 중심이다.
쌓인 설계를 바탕으로 다음을 단계적으로 넓혀 간다.

- **설계 검증 확대** — 기능 단위 점검을 설계 전체로 넓혀서, 계층 사이에 서로 맞지 않는 곳과 빠진 곳을 찾는다.
- **변경 영향도 분석** — 지금의 컬럼 사용처 조회를 넘어, 컬럼 변경·삭제가 어느 화면과 기능에 영향을 주는지 판단한다.
- **산출물 확대** — 요구사항 추적표, 속성·컬럼 정의서.
- **설계 재사용** — 검증된 설계 패턴을 다른 프로젝트에서 가져다 쓴다.
- **공공 데이터 표준화 연계** — 표준화닷컴과 연계해 테이블·컬럼을 공공 데이터 표준에 맞게 검토한다.

---

## 요약

> 설계는 사람이 AI와 대화하며 결정한다.
> 스펙코드는 그 결정이 대화창에서 사라지지 않도록 **정해진 구조에 남기고**,
> 남긴 것을 **AI가 바로 쓸 수 있는 MD**로 돌려준다.
> 그래서 팀과 다음 담당자와 유지보수하는 AI가 **같은 설계를 근거로** 일할 수 있다.
